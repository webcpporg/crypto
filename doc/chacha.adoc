[#crypto-chacha]
=== ChaCha20-Poly1305

*ChaCha20-Poly1305* is authenticated encryption built from two of Daniel J.
Bernstein's designs: the stream cipher ChaCha20 encrypts, and the one-time
authenticator Poly1305 computes a 16-byte tag over the ciphertext and the
associated data
(link:https://en.wikipedia.org/wiki/ChaCha20-Poly1305[Wikipedia];
link:https://www.rfc-editor.org/rfc/rfc8439[RFC 8439]). A chat app seals each
message with it, a password manager each entry of its vault: whoever copies
the ciphertext learns nothing of the text, and a single changed bit makes
`open` refuse it. ChaCha20 is made of additions, XORs and rotations of 32-bit
words (link:https://www.rfc-editor.org/rfc/rfc8439#section-2.1[RFC 8439,
section 2.1]), with no table indexed by a secret, so it needs no AES
instructions to be fast and is not sensitive to timing attacks in plain
portable code, as libsodium's documentation says
(link:https://doc.libsodium.org/secret-key_cryptography/aead[libsodium, AEAD
constructions]): on a phone or a WebAssembly page without AES hardware it is
the safe choice. It is a cipher suite of TLS 1.3
(link:https://www.rfc-editor.org/rfc/rfc8446#section-9.1[RFC 8446]) and the
AEAD of WireGuard (link:https://www.wireguard.com/protocol/[WireGuard]).

`ciphers::aead<Family, Backend>`, in `<webcpp/crypto/ciphers/aead.hpp>`, is
one-shot authenticated encryption in place over a family; three aliases, in
`<webcpp/crypto/ciphers/chacha20_poly1305.hpp>`, name its three
ChaCha20-Poly1305 families on their default backend, libsodium on every
target:

* `chacha20_poly1305<>`, RFC 8439's form: a 32-byte key, a 12-byte nonce, and
messages of at most 2^38^ - 64 bytes;
* `chacha20_poly1305_original<>`, the original form libsodium keeps: an 8-byte
nonce, too short to draw at random, which a counter numbers
(link:https://doc.libsodium.org/secret-key_cryptography/aead/chacha20-poly1305[libsodium]);
* `xchacha20_poly1305<>`: a 24-byte nonce, safe to draw at random for every
message (link:https://datatracker.ietf.org/doc/html/draft-irtf-cfrg-xchacha[the
XChaCha draft]). When in doubt, this one, as <<crypto-ciphers>> says: a
program that draws each nonce at random has nothing to count and nothing to
store, on the web and natively alike.

Each is made with `from_key(key_bytes)` and works in place, as AES-GCM's one-shot
calls do: `seal(nonce_bytes, associated_data_bytes, data_bytes)` encrypts
`data_bytes` and returns the 16-byte tag; `open(nonce_bytes,
associated_data_bytes, data_bytes, tag_bytes)` checks the tag and decrypts.
A failed `open` zeroes `data_bytes`; a guard's refusal leaves it untouched.
The nonce may lie in `data_bytes`, and the associated data may touch it, as a
wire format that puts it just before the message does, but not overlap it.

RFC 8439's form also runs on BearSSL, on every target, and on OpenSSL,
natively and on WASI, with the same results byte for byte: name the backend in
the type, as in `chacha20_poly1305<backends::bearssl>`, and link its library.
On BearSSL nothing allocates; on OpenSSL `from_key` allocates and a message does
not.

*Limits.* Each form bounds how much one key may seal, and how many messages
may take a nonce drawn at random before two of them risk the same one, which
would reveal both plaintexts' XOR and let tags be forged:

[cols="2,2,2"]
|===
|Form |One message, at most |Messages with random nonces, per key

|`chacha20_poly1305` |2^38^ - 64 bytes, about 256 GB |2^32^
|`chacha20_poly1305_original` |no practical limit |2^16^: use a counter
|`xchacha20_poly1305` |no practical limit |no practical limit
|===

A program changes keys periodically. A large message is no reason to improvise:
splitting a message into chunks is safe only when each chunk's tag also
covers its number and a flag marking the last chunk, in the associated data or
in a nonce built from them, and a reader refuses chunks out of order and a
stream that ends without the last flag: otherwise whoever holds the ciphertext
reorders, drops, repeats or truncates chunks and each one still opens. The
STREAM construction (link:https://eprint.iacr.org/2015/189[Hoang, Reyhanitabar,
Rogaway and Vizár, 2015]) and libsodium's secretstream
(link:https://doc.libsodium.org/secret-key_cryptography/secretstream[libsodium's
documentation]) do this; this version of crypto offers neither.

*Example.* A chat app's messages under one conversation key, each sealed with
a nonce drawn for it and the conversation's id as associated data, so that a
message moved to another conversation does not open:

[source,cpp]
----

----

[source,cpp]
----
include::{examples}/xchacha_seal.cpp[tag=open]
----

[listing]

----

[#crypto-chacha-guards]
==== The guards

Each function checks its guards first, in the order of the table, and returns
before it reads a byte of the data; the last two rows are the failures of the
work itself:

[cols="3,1"]
|===
|Condition |Error

|`from_key`: a key of another size than 32 bytes |`invalid_key_size`
|any other function: the object was moved from |`invalid_state`
|a nonce of another size than the family's, 12, 8 or 24 bytes |`invalid_iv_size`
|`open`: a tag of another size than 16 |`invalid_tag_size`
|a message longer than `max_message_size` |`message_too_long`
|`open`: the tag does not match |`authentication_failed`
|the backend fails where it should not |`backend_failure`
|===

[#crypto-chacha-pitfalls]
==== Pitfalls

* A nonce is never repeated under one key: two messages under one key and one
nonce reveal the XOR of their plaintexts and let an attacker forge tags for
every later message
(link:https://www.rfc-editor.org/rfc/rfc8439#section-4[RFC 8439, section 4]).
With `xchacha20_poly1305` draw 24 bytes at random per message; with
`chacha20_poly1305` count, a restart included, or draw at random within the
limit above; with the original form, count.
* The tag covers the ciphertext and the associated data, nothing else: what
the message belongs to (a conversation, a user, a record's id) goes in the
associated data, or a message can be moved there unnoticed.
* A failed `open` zeroes the data: keep the ciphertext if it is needed after a
failure, and never act on a message before `open` succeeds.
