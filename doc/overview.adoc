[#crypto-overview]
== Why crypto

Cryptography is what keeps a program's secrets secret and its data honest when
someone else can read or change the bytes: a database copied by an intruder, a
message passed through a relay, a cookie handed to a browser, a key that
controls money. A program that gets it wrong rarely fails a test; it fails
when an attacker reads what was meant to be secret, or forges what was meant
to be trusted. crypto exists so that a {cpp} program gets it right on every
target, with the same code.

It offers:

* *Authenticated encryption.* AES-GCM with keys of 16, 24 and 32 bytes, which
keeps a message secret and detects any change to it.
* *Randomness.* A `random_device` that reads the operating system's or the
browser's generator, and nothing else.
* *secp256k1.* BIP 340 Schnorr signatures, ECDSA signatures, their
verification, ECDH, ECDSA's strict DER and low-S forms, and the x-only tweak,
through libsecp256k1.
* *P-256.* ECDSA over SHA-256, signed low S, ECDH, strict DER and low-S forms,
and SPKI and PKCS#8 keys, through BearSSL.
* *One way to sign.* Every key pair signs with `sign(scheme, input)`, and
`crypto::verify(scheme, signature, input, public_key)` checks the signature,
the scheme named at every call and a digest given only as
`+crypto::prehashed{digest}+` (<<crypto-curves-signatures>>). Each operation
has the member and its free form, and, where WebCrypto has the algorithm,
their asynchronous forms, with one implementation
(<<crypto-curves-four-forms>>).
* *`secure::constant_time_equal`* for tags and MACs, Boost.Hash2's included, and
*`secure::erase_secret`*, which zeroes a buffer of the program's with stores the
optimiser keeps: webcpp::secure's, which crypto depends on, as is the
self-wiping `secure::secret<N>` every secret crypto returns is.
* *The AES block cipher,* a building block for the rare case that needs one.

The algorithms are not webcpp's. Each runs on a backend, a C library that
webcpp wraps behind an interface shaped as Boost.Hash2's. A backend is named
after its library: `backends::bearssl`, `backends::openssl`,
`backends::ctaes` and `backends::secp256k1`. Every call is synchronous: with C
code on every target, nothing waits.

[#crypto-overview-rules]
=== Three rules

Three rules run through every chapter, each because its absence is how real
programs were broken.

* *Never write your own cryptographic primitive.* crypto writes none either:
every cipher, mode and curve is a C library that has been reviewed and used for
years. webcpp adds a uniform {cpp} interface on top, and the checks that the C
interfaces leave to their caller.
* *Every failure is a value.* Each operation returns
`boost::system::result<T>`. Nothing fails silently: a wrong key size, a forged
message or an empty entropy pool each has its own error (<<crypto-errors>>).
* *Secrets do not outlive their use.* Keys and key schedules are wiped when an
object is destroyed or moved from, a failed `open` zeroes the bytes it
decrypted, and an object moved from refuses every operation instead of using a
wiped key.

[#crypto-overview-namespaces]
=== Namespaces and headers

crypto holds primitives only; a protocol built on them (a Bitcoin, Ethereum or
Nostr rule) belongs to a domain library, which <<crypto-wallets>> shows how to
build. Its names are grouped by kind, one chapter each, and the headers mirror
the namespaces as `<webcpp/crypto/<group>/<name>.hpp>`:

* `webcpp::crypto`: `random_device`, `error` and the configuration
(<<crypto-protecting-secrets>>, which also shows webcpp::secure's
`secure::constant_time_equal`, `secure::erase_secret` and `secure::secret<N>`); the
signatures' schemes, `prehashed` and `verify` (`<webcpp/crypto/signing.hpp>`),
the key pair concepts, `sign` and `agree` (`<webcpp/crypto/keypair.hpp>`), the
factories `from_secret`, `from_bytes`, `from_key` and `generate`
(`<webcpp/crypto/factories.hpp>`), `supports_v`, whether a backend has an
algorithm on the target (`<webcpp/crypto/supports.hpp>`; <<crypto-backends>>),
and the asynchronous family (`<webcpp/crypto/async.hpp>`; <<crypto-root>>,
<<crypto-curves-four-forms>>, <<crypto-async>>);
* `webcpp::crypto::pem`: `armour`, `unarmour`, `armoured_size` and the labels,
a key's DER as PEM text (`<webcpp/crypto/pem.hpp>`; <<crypto-key-formats>>);
* `webcpp::crypto::ciphers`: `aes128`, `aes192`, `aes256`, `gcm`, `aes128_gcm`,
`aes256_gcm`, `chacha20_poly1305`, `chacha20_poly1305_original` and
`xchacha20_poly1305` (<<crypto-ciphers>>);
* `webcpp::crypto::secret_key_encryption`: `secretbox`,
`secretbox_xchacha20poly1305`, the box forms and `aead`, the AEAD contract
(<<crypto-secret-key-encryption>>);
* `webcpp::crypto::curves::secp256k1`: key pairs, signatures, ECDH, the
encodings and the x-only tweak on secp256k1 (<<crypto-curves>>);
* `webcpp::crypto::curves::ed25519` and `curves::x25519`: Ed25519's key pairs
and signatures, X25519's key pairs and agreement, and the conversion between
them (<<crypto-ed25519>>, <<crypto-x25519>>);
* `webcpp::crypto::curves::p256`: key pairs, ECDSA, ECDH and the encodings on
P-256 (<<crypto-p256>>);
* `webcpp::crypto::public_key_encryption`: `box`, `box_xchacha20poly1305` and
`sealed_box` (<<crypto-public-key-encryption>>);
* `webcpp::crypto::key_exchange`: `kx_keypair`, libsodium's `crypto_kx`
(<<crypto-key-exchange>>);
* `webcpp::crypto::backends`: the backends (<<crypto-backends>>).

`<webcpp/crypto.hpp>` includes every header whose backend the program links.

[#crypto-overview-hash2]
=== What stays with Boost.Hash2

Hashing and HMAC are Boost.Hash2's: SHA-1, SHA-2, SHA-3, RIPEMD, BLAKE2 and
`boost::hash2::hmac<H>`. crypto offers no second interface for them, and its
examples use Hash2 wherever a hash is needed: a key derived with HKDF
(link:https://www.rfc-editor.org/rfc/rfc5869[RFC 5869]) is written on Hash2's
`hmac` in a few lines (<<crypto-p2p-session>>). What Hash2's users need beside
it is webcpp::secure's `secure::constant_time_equal`, which crypto depends on:
the `operator==` of Hash2's digests is `memcmp`, which is not constant time, so
a MAC is never checked with it (<<crypto-constant-time-equal>>).
