[#crypto-secretbox]
=== Secret boxes

A *secret box* is NaCl's name for authenticated encryption under one secret
key, with no associated data: the box hides the message and its tag proves it
unchanged (link:https://nacl.cr.yp.to/secretbox.html[NaCl];
link:https://doc.libsodium.org/secret-key_cryptography/secretbox[libsodium's documentation]).
Its cipher is XSalsa20, Salsa20 with a 24-byte nonce
(link:https://cr.yp.to/snuffle/xsalsa-20081128.pdf[Extending the Salsa20 nonce]),
and its authenticator Poly1305. A program that stores records or files under
one key, each with a nonce drawn at random, and a program that must read
what libsodium's `crypto_secretbox` wrote, use it.

`secret_key_encryption::secretbox<>` and
`secret_key_encryption::secretbox_xchacha20poly1305<>`, in
`<webcpp/crypto/secret_key_encryption/secretbox.hpp>`, name
`secret_key_encryption::basic_secretbox` over libsodium's `crypto_secretbox`
and its XChaCha20 twin, `crypto_secretbox_xchacha20poly1305`, on libsodium,
their default on every target: a 32-byte key, a 24-byte nonce safe to draw at
random for every message, a 16-byte tag. Each is made by `from_key(key_bytes)`
and works in place, with no associated data, an `authenticated_box`
(<<crypto-box-forms>>):

* `seal(nonce_bytes, data_bytes)` encrypts `data_bytes` in place and returns
its 16-byte tag, a `boost::hash2::digest<16>`;
* `open(nonce_bytes, data_bytes, tag_bytes)` checks the tag and decrypts
`data_bytes` in place, which a failed open zeroes.

Their free forms are the box forms, `secret_key_encryption::seal(box, nonce,
data)` and `secret_key_encryption::open(box, nonce, data, tag)`, and the free
`crypto::from_key<secretbox<>>(key_bytes)`. The guards are the AEADs'
(<<crypto-chacha>>), in order: a box moved from, the nonce's size, the tag's,
the length. The nonce may lie in the data: libsodium reads it again after it
writes the first bytes of the ciphertext, so it is copied first.

*Pitfalls.*

* The secret box's tag covers the ciphertext alone: a field that travels in
clear and must not change, a record's id for instance, belongs in an AEAD's
associated data (<<crypto-chacha>>), not beside a secret box.
* A nonce is never repeated under one key: draw 24 bytes at random for every
message, which never collide in practice.

*Example.* A file-sharing app seals each file in a secret box under a key
drawn for that file, and sends the key to the recipient in a sealed box
(<<crypto-sealed-box>>); the recipient opens the key, then the file, and a
changed upload does not open:
