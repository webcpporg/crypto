[#crypto-backends]
== The backends

A backend is a C library that crypto wraps; the program links the ones it names in
its Jamfile, and webcpp builds each from its sources, file by file. This page
describes ctaes and libsecp256k1; the AEAD backends are in their own pages.

[#crypto-backends-ctaes]
=== ctaes

[cols="1,3"]
|===
|Jamfile name |`/third_party//ctaes`
|Targets |native, wasip2, wasip3, emscripten
|Library |ctaes, as Bitcoin Core v31.1 ships it (`src/crypto/ctaes`)
|Licence |MIT
|Tables |none
|Allocation |none: the key schedule lives inside the crypto object
|Exports |`aes128`, `aes192` and `aes256` of `backends::ctaes`, in `<webcpp/crypto/backends/ctaes.hpp>`: the AES block cipher alone, constant time, with no mode; the C API of `<ctaes.h>`
|===

GCM is not available on ctaes: see <<crypto-block-gcm>>.

[#crypto-backends-secp256k1]
=== libsecp256k1

[cols="1,3"]
|===
|Jamfile name |`/third_party//secp256k1`
|Targets |native, wasip2, wasip3, emscripten
|Library |libsecp256k1 v0.8.0, built from its sources with every module on, recovery included
|Licence |MIT
|Tables |the feature `webcpp-secp256k1-tables`: `auto` (the default: small on Emscripten, large elsewhere), `small` (window 2, comb 2x5) or `large` (window 15, comb 11x6)
|Allocation |the signing context, in the user's resource; none elsewhere
|Exports |the C API of `<secp256k1.h>` and its modules
|===

The small tables make a program about 1 MB smaller, and verification about a
third slower. The configuration enters the canary, so a program cannot be linked
with tables other than those it was compiled for. With MSVC the static library
needs `SECP256K1_STATIC`, which the target's usage requirements define. A
program has one copy of libsecp256k1: the library's tables are global symbols, so
webcpp's build is never linked with another copy, an external one included.
