[#crypto-ed25519]
=== Ed25519

`<webcpp/crypto/curves/ed25519.hpp>` is Ed25519, the Edwards-curve signature
scheme of RFC 8032 (link:https://www.rfc-editor.org/rfc/rfc8032[RFC 8032]), on
libsodium (`/third_party//sodium`, or `/webcpp/crypto//ed25519-default`, which
links it on every target), in the namespace `webcpp::crypto::curves::ed25519`.
A signature is 64 bytes over a message of any length, made with a 32-byte
secret key, the seed, and checked with a 32-byte public key. The signature is
deterministic: the same key and message always give the same signature, so no
weak generator at signing time can leak the key. Ed25519 is the signature of
SSH keys (link:https://www.rfc-editor.org/rfc/rfc8709[RFC 8709]), of Tor's
identity keys (link:https://spec.torproject.org/cert-spec.html[Tor's
specifications]) and of Solana's accounts
(link:https://solana.com/docs/core/accounts[Solana's documentation]); browsers'
WebCrypto has it too (link:https://www.w3.org/TR/WebCryptoAPI/[W3C]). Bitcoin,
Ethereum and Nostr sign on secp256k1 instead (<<crypto-secp256k1>>).

A `keypair` is made from a seed with `from_secret(seed)`, or drawn from
`random_device` with `generate()`; it gives its public key (`public_key()`),
its seed back (`secret()`, a `secret<32>`), signs
(`sign(crypto::eddsa, message)`), and gives its X25519 secret key
(`x25519_secret`, a `secret<32>`), so that one seed serves for signatures and
for key agreement. The key pair wipes its secret key when it is moved from and
destroyed. `crypto::verify(crypto::eddsa, signature, message, public_key)`
checks a signature with the public key alone. The scheme `crypto::eddsa` signs
the message itself, of any length: a `crypto::prehashed` digest does not
compile, and the key pair is a `crypto::keypair`, as every curve's is
(<<crypto-curves-signatures>>).

A `public_key` is the 32 bytes of RFC 8032's encoded point: `public_key::from_bytes`
makes one from them, checking their size alone, and `bytes()` gives them back.
Whether the point is canonical and not of small order is the verification
policy's to judge, so a key that `crypto::verify` refuses can still be made.

Each operation has its four forms, the member and its free form, synchronous
and asynchronous, with the same work, errors and refusals
(<<crypto-curves-four-forms>>); `public_key::from_bytes(bytes)` and
`crypto::from_bytes<public_key>(bytes)` make the public key, synchronously only.
Verification takes the policy as an optional last argument, before the token
in the asynchronous forms. An asynchronous form needs
`<webcpp/crypto/async.hpp>` and `<library>/webcpp/asio//asio` in the Jamfile:

*Ed25519ph* signs the SHA-512 of a message instead of the message: a program
that signs a large file reads it in pieces, gives each to `update`, and signs
once at the end. Its type names the hash, `ph<webcpp::hash::sha2_512>`, which
the header brings with it, since RFC 8032 fixes it; another hash does not
compile. It signs with a key pair, `sign(key_pair)`, and verifies with
`verify(signature, public_key)`, the signature first, as in every `verify`.
An Ed25519ph signature is not an Ed25519 signature of the
same message, and neither verifies as the other: a protocol says which of the
two it uses.

*Strict verification.* Implementations of Ed25519 disagree on some signatures
that no honest signer produces: a scalar `S` not reduced below the group order,
a point encoded in a non-canonical form, a public key of small order.
`crypto::verify` takes a verification policy as its last argument,
`curves::ed25519::strict` by default and the only one in this version:
libsodium's rules, which refuse all three
(link:https://doc.libsodium.org/public-key_cryptography/public-key_signatures[libsodium's documentation]).
Every valid signature of Wycheproof's EdDSA file is accepted and every invalid
one refused (`ed25519_wycheproof_sodium`).

*The twelve edge cases.* Chalkias, Garillot and Nikolaenko, "Taming the many
EdDSAs" (link:https://eprint.iacr.org/2020/1244[IACR ePrint 2020/1244]), give
twelve signatures on which implementations disagree, in their suite
(link:https://github.com/novifinancial/ed25519-speccheck[novifinancial/ed25519-speccheck]).
They run against every Ed25519 backend: its own verdict (raw), and its verdict
under `strict`, which is libsodium's on every backend. The test
`ed25519_speccheck` asserts the table below, so that a new version of a backend
that changes a verdict fails until the table is regenerated. WebCrypto in node
is an outside view, recorded with the node and the OpenSSL that gave it (node's
Ed25519 is OpenSSL's) and never held to `strict`. The suite's results of 2021
show OpenSSL 3.0 accepting cases 0 to 2 and 11; the newer OpenSSL of the
column's node refuses them, as libsodium does.

Honest signatures verify everywhere: the cases differ only on signatures no
honest signer makes, and a network that mixes verifiers must agree on one rule
for them. In the suite's results of 2021
(link:https://github.com/novifinancial/ed25519-speccheck#results[the suite's
results], whose `Cargo.toml` pins them), Rust peers that used the default
`verify` of ed25519-dalek 1.0.0-pre.4 accepted cases 0 to 2 and 11, which
`strict` refuses, and ed25519-zebra 2.1.1, a ZIP-215 verifier
(link:https://zips.z.cash/zip-0215[ZIP 215], the rule of Zcash), accepted every
case but 6 to 8. ZIP-215 does so by design: it verifies with the
cofactor and accepts non-canonical encodings of `A` and `R`, so that every
ZIP-215 verifier agrees on every signature. `strict` refuses the cases ZIP-215
accepts beyond it; `zip215` is not a policy of this version, and waits for a
mature C or {cpp} implementation of ZIP-215.

*Pitfalls.*

* Keep the seed out of logs, crash reports and source control: whoever holds it
signs as the key's owner. The examples use RFC 8032's published seeds only to
print fixed signatures.
* A signature proves who signed the bytes, not when or for what: a protocol
that must refuse a replayed message signs a counter, a time or a context with
it.
