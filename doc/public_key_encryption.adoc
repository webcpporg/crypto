[#crypto-public-key-encryption]
== Public-key encryption: `webcpp::crypto::public_key_encryption`

*Public-key encryption* encrypts to a public key: a key agreement, on public
keys, gives a secret key, and a fast cipher encrypts the data under it, the
construction textbooks call hybrid encryption
(link:https://en.wikipedia.org/wiki/Hybrid_cryptosystem[Wikipedia]). A chat app
encrypts a message to a contact whose public key it knows; a feedback form
encrypts a report to a key whose owner alone may read it. The namespace
`webcpp::crypto::public_key_encryption` holds NaCl's and libsodium's
constructions in this version: the box, between two key pairs, and the sealed
box, from anyone to a public key. Both agree with X25519 (<<crypto-x25519>>)
and seal with XSalsa20-Poly1305, the secret box's cipher (<<crypto-secretbox>>),
or, for `box_xchacha20poly1305`, XChaCha20-Poly1305, on libsodium, their
default on every target. The namespace is named by the problem it solves: the
word hybrid now names the post-quantum hybrids, as X25519MLKEM768 and X-Wing,
for which `webcpp::crypto::hybrid` is kept free, and a later HPKE
(link:https://www.rfc-editor.org/rfc/rfc9180[RFC 9180]) joins the boxes here.

*Which one.* A box when the two parties know each other's public keys and the
recipient must know the message came from the other: a chat between two
contacts. A sealed box when anyone may write and the recipient alone reads: a
feedback form, a drop box, a file key sent to a recipient known by a public key
(<<crypto-everyday-files>>). `box_xchacha20poly1305` only when the peer uses
libsodium's XChaCha20 form; otherwise `box`, NaCl's format, which libsodium
and its bindings in every language read. Without either, a program that
encrypts to a public key by hand, an agreement and a cipher of its own
choosing, risks the mistakes these constructions settle: a shared secret used
as a key, a nonce reused, a weak public key accepted.

[#crypto-box]
=== Boxes

`public_key_encryption::box`, in
`<webcpp/crypto/public_key_encryption/box.hpp>`, is NaCl's `crypto_box`
(link:https://nacl.cr.yp.to/box.html[NaCl];
link:https://doc.libsodium.org/public-key_cryptography/authenticated_encryption[libsodium's documentation]).
`box::from_keys(secret_key, peer_public_key)` agrees a key from the own X25519
secret key and the peer's public key, once for the pair (libsodium's
`beforenm`); the box then works in place, as an AEAD without additional data:
`seal(iv_bytes, data_bytes)` encrypts and returns the 16-byte tag, and
`open(iv_bytes, data_bytes, tag_bytes)` checks it and decrypts, zeroing the
data when it does not match. Alice's box made from her secret key and Bob's
public key, and Bob's made from his secret key and Alice's public key, hold
the same key: what one seals the other opens. `box_xchacha20poly1305` is
libsodium's `crypto_box_curve25519xchacha20poly1305`, the same with
XChaCha20-Poly1305. A box is moved and not copied, and wipes its key when
moved from and destroyed.

A peer's public key of small order makes the shared secret one an attacker
knows: `from_keys` refuses it with `weak_public_key`, as libsodium's `beforenm`
does.

*Pitfalls.*

* A box proves that one of the two key pairs wrote a message, not which one:
a protocol that needs to know says so inside the message, or signs it.
* A nonce is never repeated for one pair of keys, in either direction: draw
24 bytes at random for every message.

[#crypto-sealed-box]
=== Sealed boxes

`public_key_encryption::sealed_box`, in
`<webcpp/crypto/public_key_encryption/sealed_box.hpp>`, is
libsodium's sealed box, `crypto_box_seal`
(link:https://doc.libsodium.org/public-key_cryptography/sealed_boxes[libsodium's documentation]):
anyone who knows a public key can seal a message to it, and only the key pair
opens it. `seal(recipient_public_key, message, out)` writes to `out`, of the
message's size plus `overhead`, 48 bytes, a key pair libsodium draws for the
message, its public key, the tag and the ciphertext, and wipes the drawn
secret key; the nonce comes from the two public keys. `open(recipient_public_key,
recipient_secret_key, sealed, out)` writes the message to `out`, of the sealed
box's size less 48 bytes, and zeroes `out` when the box does not open: sealed to
another key pair, or changed. The sizes are checked first
(`invalid_input_size`), then the keys (`invalid_public_key`,
`invalid_key_size`).

include::generated/backends-sealed_box.adoc[]

*Pitfalls.*

* A sealed box is anonymous: the recipient cannot tell who sealed it, nor
whether an attacker did. Where the sender matters, use a box or a signature.
* The sender cannot open what it sealed: it keeps its own copy of the
message if it needs one.

*Example.* A file-sharing app seals each file's key to its recipient:
<<crypto-everyday-files>>.
