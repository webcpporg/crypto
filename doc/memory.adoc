[#crypto-memory]
== Allocation

An audio worklet, a game loop or an embedded device must not allocate on its
hot path, or must allocate only from its own arena. crypto's own code allocates
one thing: a secp256k1 key pair's signing context, once, in `keypair::make`
and in `generate`, which allocates through `make`,
from the `std::pmr::memory_resource` the program passes, which must outlive the
key pair. A resource that cannot allocate throws, as the standard has it, and
`make` lets the exception through; without exceptions such a resource ends the
process. It never returns null (<<crypto-memory-openssl>> says why). Every
buffer is the caller's.

* *Nothing allocates per message, on any backend:* `seal`, `open`,
`begin_seal`, `update`, `result`, `begin_open`, `authenticate`, `verify`,
`end_open`, `encrypt`, `decrypt` (the block cipher's and the incremental
open's), `fill`, the signatures (hedged and recoverable too), `ecdh`, `ecdh_x`,
`ecdh_point`, the verifications, `recover`, `parse_public_key`, `serialize_public_key`, the tweaks and negations,
`pubkey_combine` (in a `workspace` the caller lends), the SPKI and PKCS#8
encoders and decoders (`decode_pkcs8` makes a key pair, whose context is the one
allocation above), and `ellswift_*`, MuSig2's functions and silent payments'
(each over a `workspace` the caller lends, where it takes one). The counting
tests of `test/` prove it, every `operator new` and the C library's allocator
counted.
* *BearSSL and ctaes allocate nothing,* `make` included: the key schedule lives
inside the object.
* *OpenSSL's `make` allocates its cipher context through OpenSSL's own
allocator,* outside the program's resource; the first `make` of a process also
initialises OpenSSL. The test `allocation_openssl` counts and prints these
allocations on each target at every run, and fails if a message allocates; the
count depends on the target and on OpenSSL's build, so the page does not copy
it. A program that needs every allocation in its arena uses BearSSL, or
OpenSSL with the memory option of <<crypto-memory-openssl>>, natively.
* *Keys are wiped.* The key schedules that live inside crypto's objects
(BearSSL's, ctaes's, libsecp256k1's key pair) are overwritten on destruction
and on move by stores the optimiser cannot drop; OpenSSL wipes its own
contexts when they are freed.
* *No type is shareable.* An object holds a key, and OpenSSL's hold pointers
into OpenSSL's heap: none is placed in memory shared with another process,
and a key never should be.

[#crypto-memory-openssl]
=== OpenSSL's allocations in your own memory resource

By default OpenSSL allocates with the C library's `malloc`, outside every
allocator of the program's. A native program that keeps its memory in its own
arena, such as an audio engine whose real-time thread may not touch the
system's heap, or an embedded server that gives each part a fixed budget,
finds OpenSSL bypassing that arena: its first `make` initialises OpenSSL, which
takes many blocks from the system's heap, and Beast's TLS and
libdatachannel's DTLS, which link the same OpenSSL, allocate there for every
connection. The arena's accounting is then wrong, a budget is exceeded with no
warning, and a real-time thread can wait on the system allocator's lock. The
memory option sends every allocation OpenSSL makes in the process to a
`std::pmr::memory_resource` the program defines. It is for native programs
only: on WebAssembly the backend is BearSSL, which allocates nothing.

*How.* Three things, each needed:

. *The define and OpenSSL, in the requirements of the program's project,*
so that every target of the program gets both, its own libraries and a tool
that only calls `random_device` included. `config.hpp` stops a target that has
the define without OpenSSL, and any build for WebAssembly, with an `#error`
(<<crypto-jamfile-memory>>):

*What to know.*

* *The whole process.* The resource receives every allocation of the OpenSSL
the program links, not only crypto's: Beast's TLS and libdatachannel's DTLS
too. The test `neighbours` links Asio's TLS and libdatachannel beside the
option, with the objects of libdatachannel whose static initialisers name
OpenSSL, and the install still succeeds; the test `handshake` runs a TLS 1.3
handshake through libssl, and counts no call of the C library's allocator over
the whole exchange: the key, the certificate, both contexts, the handshake, a
record each way and every free.
* *Nothing else may call `CRYPTO_set_mem_functions`.* If another library has
called it before, `install_memory_functions()` returns
`memory_functions_refused`; if it calls it after the install, the next `make`
returns `memory_functions_not_installed`, and only when that call has finished
before the `make`. The damage is done by then: OpenSSL accepts the replacement
after the install, and from then on frees the blocks it took from the resource
through the other party's `free`, which corrupts that party's heap; the
error that `make` then returns does not undo it.
* *`memory_functions_refused` although the install is the first statement of
`main`* means that something used OpenSSL before `main`: a static object of
another library. OpenSSL then keeps its own `malloc` for the rest of the
process. A libcrypto DLL, which webcpp never builds (a program built without
b2), is refused the same way.
* *`memory_functions_not_installed` from a `make`* means that the install was
not called, or that something replaced OpenSSL's functions after it.
* *One module.* The program's code that uses crypto's OpenSSL backend lives in
one module: a DLL, or a shared library of the program's that hides its
symbols, that includes the backend's header has its own copy of crypto's
functions, and its `make` returns `memory_functions_not_installed`. An ELF
shared library with default visibility usually binds to the executable's
copy instead, but nothing guarantees it.
* *Threads on Windows.* OpenSSL gives a thread's own blocks back when the
thread ends, except on Windows, where the static libcrypto that webcpp always
builds is never told that a thread ends. Every thread that used OpenSSL, a
`make`, Beast's TLS or libdatachannel's DTLS, leaves its error queue and its
list of handlers in the resource, never given back, not even at exit, unless
it calls `OPENSSL_thread_stop()` before it ends. A resource of a fixed size
under a thread pool that replaces its threads, or a thread per connection,
then runs out over time, and the failure lands in a later `make` or inside a
TLS handshake. The example's worker thread ends so, and so does the second
thread of the test `everything`, whose exit check fails on Windows without it:
+
[source,cpp]
----
include::{examples}/openssl_memory.cpp[tag=thread,indent=0]
----
* *When the resource cannot allocate.* The resource must serve OpenSSL's
initialisation, which the first use of OpenSSL in the process runs, usually the
first `make`. On an OpenSSL built with threads, which is MSVC's only build and
b2's `threading=multi` elsewhere, a failure during OpenSSL's base initialisation
is not recoverable: OpenSSL reports it through its error queue, whose state
needs the initialisation that is running, so OpenSSL re-enters its own
initialisation and that call never returns. The process aborts on macOS,
deadlocks on Linux and spins on Windows. Only an OpenSSL built without threads,
b2's default on macOS and Linux, returns from that failure, and OpenSSL stays
unusable for the rest of the process: `make` gives `backend_failure` from then
on. When the failing allocation is OpenSSL's base initialisation (with OpenSSL
3.5.9, its first lock), OpenSSL never registers its cleanup, and
`OPENSSL_cleanup` frees nothing: the blocks it took meanwhile stay in the
resource until the process ends, and the thread's error queue takes no entry
from then on. The test `fail_init` pins this on an OpenSSL without threads and
prints how many blocks stay; with threads, as `fail_init_threads`, it prints how
many blocks the first `make` took instead. After the initialisation, `make`
gives `not_enough_memory` or `backend_failure`. `seal` and `open` allocate
nothing. A resource of a fixed size needs room for the first `make`, whose
allocations the test `allocation_openssl` prints on each run. A resource
reports that it cannot allocate as the standard has `do_allocate` report it,
by throwing, `std::bad_alloc` or another exception, which the adapter turns
into OpenSSL's null. It never returns null: libc++ and libstdc++ declare
`allocate` never to return null, so the optimiser removes any check of its
result, and a null is written through in a release build. Without
exceptions, a resource that cannot allocate ends the process, as `std::pmr`'s
own resources do, and the failures above are not reached.
* *Two allocations stay outside the resource,* because no hook of OpenSSL's
reaches them: the C library's `FILE` and its buffer while OpenSSL reads its
configuration file at initialisation (one or two blocks, by C library, freed
when the file closes), and OpenSSL's secure heap, if the program turns it on
with `CRYPTO_secure_malloc_init`.
* *Native only.* A WebAssembly build of the same program is a project of its
own, in a directory of its own, with neither the define nor OpenSSL, and names
`/third_party//bearssl`.
