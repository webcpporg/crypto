[#crypto-wallets]
== Wallets

A *cryptocurrency wallet* holds the keys that control funds on a blockchain:
it makes them, keeps them secret, and signs the transactions that spend the
funds (link:https://en.wikipedia.org/wiki/Cryptocurrency_wallet[Wikipedia]).
Whoever holds a wallet's secret key holds its money, and a signature over the
wrong bytes spends it in a way its owner did not intend. Nothing can be
recalled: a leaked key or a wrong signature is a loss.

crypto holds the primitives a wallet needs: the key pair, the signatures, their
encodings and the tweak, each done by libsecp256k1. A blockchain's rules (BIPs,
EIPs) belong to a domain library built on top: it serializes the protocol's
messages, computes its hashes with Boost.Hash2, and calls these primitives. The
Bitcoin steps below are what such a library builds; they are not crypto's API.

[#crypto-wallets-key]
=== Making and keeping a key

*The problem.* A wallet's key must be unpredictable, must be a valid secret key
of the curve, and must survive on disk without being readable there.

*The idea.* 32 bytes from `random_device` are a valid secp256k1 secret key with
overwhelming probability; when they are not (zero, or not below the group
order), `from_secret` says so and the wallet draws again. At rest, the secret is sealed
with AES-GCM under a key the device keeps elsewhere (a platform keystore, or a
key derived from the user's passphrase by a password hash, a hashing
library's job rather than crypto's), with the wallet's format version as
associated data.

in a backup. Wipe every copy of the secret once the key pair is made.

[#crypto-wallets-der]
=== An ECDSA signature in DER

*The problem.* Bitcoin's SegWit v0 inputs carry an ECDSA signature in strict
DER (link:https://github.com/bitcoin/bips/blob/master/bip-0066.mediawiki[BIP 66])
over a hash the protocol defines
(link:https://github.com/bitcoin/bips/blob/master/bip-0143.mediawiki[BIP 143]),
in low-S form, which Bitcoin nodes require to relay a transaction (a policy;
link:https://github.com/bitcoin/bips/blob/master/bip-0146.mediawiki[BIP 146]
proposed it as a consensus rule).

*The idea.* The domain library computes the signature hash, the sighash
(SHA-256 twice over the preimage it serialized); crypto signs it as
`+crypto::prehashed{sighash}+` under `crypto::ecdsa_sha256`, which is honest, the
sighash being the SHA-256 of a SHA-256 (<<crypto-curves-signatures-bitcoin>>).
It signs deterministically and in low-S form, and `to_der` encodes the
signature as strict DER:

[#crypto-wallets-taproot]
=== A tweaked key: Taproot

*The problem.* A Taproot output key is the wallet's internal key tweaked by
`t = tagged_hash("TapTweak", internal_key || merkle_root)`
(link:https://github.com/bitcoin/bips/blob/master/bip-0341.mediawiki[BIP 341]);
spending by key path signs with the tweaked key pair.

*The idea.* The tweak is the protocol's; the addition on the curve is crypto's.
The domain library computes `t` with Boost.Hash2's SHA-256 (a tagged hash is
`SHA-256(SHA-256(tag) || SHA-256(tag) || data)`) and passes it to
`tweak_xonly`, once on the public key for the address, once on the key pair to
sign:

Without a script tree, as here, the Merkle root is omitted and the tweak
hashes the internal key alone (BIP 341). crypto checks the key and the tweak,
and wipes the pair if the tweak gives no valid key; what the tweak means is
the domain library's.

The x-only tweak is BIP 341's arithmetic: it lifts the key to the point with an
even y, and the key pair's version negates the secret key when the public
key's y is odd. It serves the protocols built on x-only keys, such as Taproot's
output key or a pay-to-contract commitment to an x-only key. It is not BIP 32's
child derivation, which adds to the parent's full point and secret key without
that negation: for the half of the parents whose public key has an odd y, an
x-only tweak derives another child than every BIP 32 wallet, whose addresses a
wallet restored from the same seed never finds. BIP 32 tweaks the full key,
with `seckey_tweak_add` and `pubkey_tweak_add` (<<crypto-secp256k1-tweaks>>),
and computes its tweak with HMAC-SHA-512, which is a domain library's
(link:https://github.com/bitcoin/bips/blob/master/bip-0032.mediawiki[BIP 32]).

*Mistakes to avoid.* A Taproot tweak is computed from public data (the internal
key and the Merkle root), so the tweaked secret key is as sensitive as the
original: anyone who knows the tweak and either secret key knows the other.
Check the domain library's tweak against BIP 341's published vectors.

[#crypto-wallets-recovery]
=== Who signed this? Recoverable signatures

*The problem.* A wallet app receives a request that another wallet signed: a
transaction to relay, or a message that proves who owns an account. The
request carries the signed bytes and the signature, but no public key, and the
app must know whose key signed it before it acts on it.

*The idea.* An ECDSA signature leaves its signer's public key one of a few
candidates; a recoverable signature adds the id, 0 to 3, of the one that
verifies, so that a reader computes the signer's key from the signature and
the hash alone. Ethereum finds a transaction's sender this way
(link:https://ethereum.github.io/yellowpaper/paper.pdf[Ethereum's yellow paper,
appendix F]). `sign(crypto::ecdsa_sha256_recoverable, input)` makes the
65-byte `recoverable_signature`, and
`recover(crypto::ecdsa_sha256_recoverable, signature, input)` finds the key (<<crypto-secp256k1-recovery>>). Recovery finds some key for almost any
signature and any hash: what makes it a check is the comparison with the key
the reader expects.

Ethereum compares addresses rather than keys, the last 20 bytes of the
Keccak-256 of the uncompressed key (the yellow paper, appendix F), and a wallet
signs a message after EIP-191's prefix
(link:https://eips.ethereum.org/EIPS/eip-191[EIP-191]), whose digest is
Keccak-256's: Ethereum's scheme is `crypto::ecdsa_keccak256_recoverable`, which
signs and recovers that digest given as `+crypto::prehashed{digest}+`
(<<crypto-secp256k1-ethereum>>, with a `personal_sign` example that prints `v`
and the address). The digest, `v` and the address are the protocol's rules,
which the program, or a domain library built on crypto, such as a future
webcpp::ethereum, computes; crypto holds the signature and the recovery. This
section names no application.

*Mistakes to avoid.* Never trust a recovered key on its own: a changed or
forged message recovers some other key rather than failing, so compare the
key, or the address made from it, with the one expected before acting. Hash
exactly what the signer hashed: a message hashed without EIP-191's prefix, or
with another, recovers another key, which looks like a wrong signer rather
than a wrong hash.

[#crypto-wallets-musig]
=== Two devices, one signature: MuSig2

*The problem.* A wallet split across a phone and a laptop, so that a thief who
takes one device takes nothing: spending needs both. A script that asks for
two signatures shows on the chain that two keys hold the coins, and costs more
to spend.

*The idea.* MuSig2 aggregates the two public keys into one, and the two
devices' partial signatures into one BIP 340 signature under it, which the
chain checks as any single signer's
(link:https://github.com/bitcoin/bips/blob/master/bip-0327.mediawiki[BIP 327]).
It takes two rounds: each device makes a nonce and sends its public half; with
both in, each signs its part, and the parts add up to the signature
(<<crypto-secp256k1-musig>>).

domain library's. This section names no application.

*Mistakes to avoid.* Reusing a nonce: two partial signatures with one nonce
give away the secret key, so a nonce is made when the signature is made, never
stored, and never restored from a backup; `partial_sign` takes it by value and
refuses one already used. Signing before every nonce is in: a device that
signs while the other can still choose its nonce lets it steer the final nonce,
which the two rounds exist to prevent
(link:https://eprint.iacr.org/2020/1261[Nick, Ruffing and Seurin, MuSig2]). A
naive key sum: the plain sum of the two public keys, `pubkey_combine`, is not
a multisignature, since a device that announces its key after seeing the
other's can choose one that cancels it and spend alone; `key_aggregate` weighs
each key by a hash of all of them (BIP 327).

[#crypto-wallets-silent]
=== A reusable address: silent payments

*The problem.* A donation page wants one address to publish for good. With a
plain address every payment to it is on the chain for anyone to list and add
up, and a fresh address for each payer needs a server that hands them out.

*The idea.* A silent payment address is two public keys, scan and spend. The
sender combines the secret keys of its transaction's inputs with the scan key
into a secret only it and the recipient share, an ECDH, and tweaks the spend
key with it into an output key that is new for each transaction; the
recipient scans each transaction with its scan secret and recognises its
outputs (link:https://github.com/bitcoin/bips/blob/master/bip-0352.mediawiki[BIP 352];
<<crypto-secp256k1-silent-payments>>).

*Mistakes to avoid.* The outpoint: it must be the smallest of all the
transaction's inputs, eligible or not; with another, the sender computes
another secret and the recipient never finds the payment. A dropped output:
every output `create_outputs` makes must be in the transaction, since the
recipient looks for them in order and stops at the first it does not find
(link:https://github.com/bitcoin-core/secp256k1/blob/6e2c8bc4ecdc6e71dbe7a368f360d8d453ce435d/include/secp256k1_silentpayments.h[libsecp256k1's silent payments header]).
Scanning cost: the recipient pays one ECDH for every transaction with eligible
inputs, its own or not, which a light client must plan for (BIP 352).
