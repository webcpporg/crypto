[#crypto-secp256k1]
=== secp256k1

`<webcpp/crypto/curves/secp256k1.hpp>` is secp256k1 on libsecp256k1
(`/third_party//secp256k1`), in the namespace
`webcpp::crypto::curves::secp256k1`. It offers two signature schemes and one
key agreement:

* *BIP 340 Schnorr signatures*, 64 bytes over a message of any length, with a
32-byte x-only public key: Bitcoin's Taproot and Nostr's events
(link:https://github.com/bitcoin/bips/blob/master/bip-0340.mediawiki[BIP 340];
link:https://github.com/nostr-protocol/nips/blob/master/01.md[NIP-01];
link:https://en.wikipedia.org/wiki/Schnorr_signature[Wikipedia]);
* *ECDSA signatures*, 64 bytes over a 32-byte hash, with a 33-byte compressed
public key: Bitcoin before Taproot and Ethereum
(link:https://en.wikipedia.org/wiki/Elliptic_Curve_Digital_Signature_Algorithm[Wikipedia];
link:https://ethereum.github.io/yellowpaper/paper.pdf[Ethereum's yellow paper]).
Each signature's nonce is RFC 6979's, derived from the key and the hash, so
that no weak generator can leak the key
(link:https://www.rfc-editor.org/rfc/rfc6979[RFC 6979]), and each is in low-S
form. A signature is also made hedged, with the caller's fresh randomness
mixed into the nonce, or recoverable, with the id from which a reader finds
the signer's key (<<crypto-secp256k1-recovery>>);
* *ECDH*, a shared secret: `ecdh` gives libsecp256k1's hashed form, the
SHA-256 of the shared point in its 33-byte compressed encoding, one of three
forms (<<crypto-secp256k1-ecdh>>). It interoperates only with peers that hash
the same way, such as another program on libsecp256k1's default; `ecdh_x`
gives the raw x coordinate that Nostr's encrypted messages
(link:https://github.com/nostr-protocol/nips/blob/master/44.md[NIP-44]) take.

A `keypair` is made from a 32-byte secret key with `make(secret)`, which
allocates its signing context in the `std::pmr::memory_resource` it is given,
and randomises it from `random_device`; crypto's own code allocates nothing
else (<<crypto-memory>>). A key pair gives its x-only public key
(`xonly_public_key`), its compressed and uncompressed ones (`public_key`,
`public_key_uncompressed`), signs (`sign_schnorr`, `sign_ecdsa`,
`sign_recoverable`), derives an ECDH secret (`ecdh`, `ecdh_x`, `ecdh_point`),
and is tweaked in place (`tweak_xonly`). `verify_schnorr` and `verify_ecdsa`
check signatures with a public key alone, and `recover` finds the key from a
recoverable signature; `parse_public_key` and `serialize_public_key` read and
write a `public_key` (<<crypto-secp256k1-keys>>); `to_der`, `from_der` (strict
DER) and `normalize_ecdsa` convert ECDSA's DER and low-S forms; and
`tweak_xonly` tweaks an x-only public key. Every function reads libsecp256k1's
canary, so that a program linked with another build of the library does not
link.

A tweak is a primitive: crypto does not compute one. A protocol that defines a
tweak (Bitcoin's Taproot output key, for one) belongs to a domain library,
which computes the tweak from its own hash and passes it here
(<<crypto-wallets-taproot>>).

*Pitfalls.*

* A secret key drawn from `random_device` is below the group order with
overwhelming probability, but not always: `make` returns
`invalid_secret_key` then, and the program draws again
(<<crypto-wallets-key>>).
* Keep the secret key out of logs, crash reports and source control: the key
pair wipes its copy, the program wipes its own.
* BIP 340's auxiliary randomness is fresh for each signature; a fixed value is
safe only because the nonce also depends on the key and the message, and the
examples use zeros only to print fixed signatures.
* `verify_ecdsa` refuses a high-S signature, as libsecp256k1 does:
`normalize_ecdsa` gives the low-S form of a signature from a signer that does
not enforce it. A verifier that normalizes before verifying accepts both forms
of a signature, so it must not rely on the signature's bytes being unique
(link:https://github.com/bitcoin/bips/blob/master/bip-0146.mediawiki[BIP 146]).

[#crypto-secp256k1-ecdh]
==== Three forms of ECDH

Two users of a chat app who have never met want to talk without the server
reading along. Each publishes a public key; with elliptic-curve Diffie-Hellman
(ECDH) each combines its own secret key with the other's public key and both
arrive at the same shared secret, which nobody who sees only the public keys
can compute
(link:https://en.wikipedia.org/wiki/Elliptic-curve_Diffie%E2%80%93Hellman[Wikipedia]).
The shared secret is a point on the curve, the secret key of one side times the
public key of the other; what a program takes of that point is a choice of the
protocol, and a key pair gives the three that protocols use:

* `ecdh`: the SHA-256 of the point's compressed encoding, 32 bytes,
libsecp256k1's default
(link:https://github.com/bitcoin-core/secp256k1#readme[libsecp256k1]). Two
programs on webcpp, or one on libsecp256k1's default, agree on it; it is the
form of the chat session of <<crypto-p2p-session>>.
* `ecdh_x`: the point's x coordinate, 32 bytes, unhashed. Nostr's encrypted
messages (link:https://github.com/nostr-protocol/nips/blob/master/44.md[NIP-44])
and Wycheproof's ECDH test vectors
(link:https://github.com/C2SP/wycheproof[Project Wycheproof, test vectors for
cryptographic libraries]) take this form; the protocol then hashes it its own
way.
* `ecdh_point`: the point itself, 65 bytes in SEC1's uncompressed encoding
(0x04, x, y; link:https://www.secg.org/sec1-v2.pdf[SEC 1, sections 2.3.3 and
2.3.4]): both coordinates, of which the other two forms keep x alone.

Each is returned as a `secret<N>`, which wipes its bytes when it is destroyed
or moved from: a program reads it with `bytes()` and makes no copy of its own
to forget. Each refuses a moved-from key pair with `invalid_state`, and a peer
key that is not a point of the curve, or not 33 bytes compressed or 65 bytes
uncompressed with the prefix 04, with `invalid_public_key`. They are members
of the key pair, whose backends are listed above.

first step follows: NIP-44's conversation key, HKDF-extract
(link:https://www.rfc-editor.org/rfc/rfc5869[RFC 5869]) of the x coordinate
with the salt `nip44-v2`. The rest of NIP-44 (message keys, padding, the
payload) is a domain library's, not crypto's:

*Pitfalls.*

* The raw x coordinate is not a key: a Diffie-Hellman value is not uniformly
random (link:https://www.rfc-editor.org/rfc/rfc5869#section-3.3[RFC 5869,
section 3.3]). It is always below the field's prime and always the x of a
point, which not every 32-byte value is
(link:https://www.secg.org/sec1-v2.pdf[SEC 1, sections 2.3.3 and 2.3.4]), so
its 256 bits hold less than 256 bits of entropy. A protocol's key derivation
function (HKDF in NIP-44) turns it into keys. Used directly as an AES key, it
is the same key in every protocol that uses the same two key pairs that way:
a key that leaks from one leaks from all of them.
* Two programs must agree on the form. One that takes `ecdh` and one that
takes `ecdh_x` derive different keys from the same key pairs, and fail
silently: every message is refused as forged, with nothing pointing at the
cause. Read the protocol's specification for the form it names.
* Never use one shared secret as two keys, one per direction or one for
encryption and one for authentication: derive one key per purpose with the
KDF, each with its own label (<<crypto-p2p-session>>).

[#crypto-secp256k1-keys]
==== Public keys and their two forms

A public key arrives as bytes: from a peer, from a file, from a transaction. A
program that checks many signatures with one key, or compares keys, parses it
once into a `public_key`, a point of the curve that the type guarantees, and
uses that from then on. The check matters: a peer's key that is not on the
curve is how invalid-curve attacks begin, in which a key off the curve,
combined with a secret key, leaks that secret bit by bit, which is why the
holder of a long-lived secret key validates the other side's public key
(link:https://en.wikipedia.org/wiki/Elliptic-curve_Diffie%E2%80%93Hellman[Wikipedia]).
`parse_public_key` makes the only `public_key` there is, so a program that
holds one holds a valid point.

A point is written in one of two forms
(link:https://www.secg.org/sec1-v2.pdf[SEC 1, sections 2.3.3 and 2.3.4]):

* *compressed*, 33 bytes: 02 or 03 by the parity of y, then x. Bitcoin writes
keys this way, and its SegWit outputs take no other form by default
(link:https://github.com/bitcoin/bips/blob/master/bip-0143.mediawiki[BIP 143]);
* *uncompressed*, 65 bytes: 04, x, y. Ethereum's keys are x and y, 64 bytes,
the uncompressed form without its prefix
(link:https://ethereum.github.io/yellowpaper/paper.pdf[Ethereum's yellow paper]).

`serialize_public_key` writes either (`point_form::compressed`, the default,
or `point_form::uncompressed`); a key pair gives its own key in both forms,
`public_key` and `public_key_uncompressed`. Two `public_key` values compare
with `==`, and order with `+<=>+` as their compressed encodings do, the order
MuSig2's key sorting uses
(link:https://github.com/bitcoin/bips/blob/master/bip-0327.mediawiki[BIP 327]). A `public_key` holds nothing secret and is copied
freely.

include::generated/backends-public_key.adoc[]

*Pitfalls.*

* X9.62's hybrid form, prefix 06 or 07 then x and y, is refused with
`invalid_public_key`, though libsecp256k1 reads it: SEC 1 defines only the two
forms above and refuses every other prefix
(link:https://www.secg.org/sec1-v2.pdf[SEC 1, section 2.3.4]), so a key webcpp
takes is one every SEC 1 parser takes, and one key has one encoding of each
form.
* A key compared as bytes, rather than parsed, differs between its two forms:
the same key compressed and uncompressed are different bytes. Parse both and
compare the `public_key` values.
* Ethereum's 64-byte key is the uncompressed form without its 04: add the
prefix before `parse_public_key`, and drop it after `serialize_public_key`.

[#crypto-secp256k1-recovery]
==== Recoverable signatures

Ethereum names an account by the hash of its public key, and a transaction
carries no key: only the signature, from which a node recovers the key that
made it
(link:https://ethereum.github.io/yellowpaper/paper.pdf[Ethereum's yellow
paper, appendix F]). An ECDSA signature fits up to four keys, and the
recovery id, 0 to 3, names the one that made it
(link:https://www.secg.org/sec1-v2.pdf[SEC 1, section 4.1.6]). `sign_recoverable`
writes 65 bytes, r, s and the id, with the same r and s as `sign_ecdsa`, and
`recover` returns the `public_key` from those 65 bytes and the hash. It
refuses with `invalid_signature` an id above 3, an r or an s not below the
group order, and a signature from which no key is recovered.

`sign_ecdsa` also has a hedged form, which takes 32 more bytes, drawn from
`random_device` and new for each signature, and mixes them into RFC 6979's
nonce, as the RFC's variant with additional data allows
(link:https://www.rfc-editor.org/rfc/rfc6979#section-3.6[RFC 6979, section
3.6]) and libsecp256k1's `ndata` takes
(link:https://github.com/bitcoin-core/secp256k1#readme[libsecp256k1]). The
signature verifies as any other.

*Pitfalls.*

* Recovery always yields some key for almost every signature and hash, a
forged one included: a program that trusts the recovered key alone accepts
anything. Compare it with the key expected, as the example does, or with the
account the key's hash must name.
* Ethereum's `v` is the recovery id plus 27, or plus an offset of the chain's
(link:https://ethereum.github.io/yellowpaper/paper.pdf[Ethereum's yellow
paper, appendix F]): passing `v` as the id makes `recover` refuse it. That
encoding, and the message hash Ethereum signs, are a domain library's.
* The hedged form gives a different signature each time, so a test that
compares signatures with fixed bytes uses the unhedged form. Use the hedged
form where the signer runs on hardware an attacker can fault or observe: the
nonce then no longer depends on the key and the hash alone, so two signings of
one hash do not repeat the same computation. Never reuse the 32 bytes: fixed
extra data leaves the signature deterministic, as plain RFC 6979.
