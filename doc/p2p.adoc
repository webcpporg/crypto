[#crypto-p2p]
== Peer-to-peer applications

In a *peer-to-peer* application the participants talk to each other rather than
through a server they trust (link:https://en.wikipedia.org/wiki/Peer-to-peer[Wikipedia]):
a chat between browsers over WebRTC, notes posted to public relays, files
shared directly. Whatever carries the bytes, a relay or a signalling server,
sees all of them and may change them. Cryptography is what lets the peers trust
each other instead: a signature proves who wrote a message, and a key agreed in
public keeps the conversation private.

[#crypto-p2p-identities]
=== Identities and sessions between peers

*The problem.* Peers of a network find each other through untrusted relays
and discovery services. Each needs a name that no one else can claim, and each
connection between two peers must be private and must reach the peer it names,
not an impostor in the middle.

*The idea.* libp2p, a peer-to-peer networking stack, does it this way: a
peer's identity is a key pair, Ed25519 among the types its specification
allows, and its id is derived from the public key
(link:https://github.com/libp2p/specs/blob/master/peer-ids/peer-ids.md[libp2p's
peer ids]); each connection agrees fresh X25519 keys and seals with
ChaCha20-Poly1305, and each side signs its connection key with its identity
key, so that the other knows whom it reached
(link:https://github.com/libp2p/specs/blob/master/noise/README.md[libp2p's
Noise handshake]). webcpp's primitives give each piece: an Ed25519 key pair and
its signatures (<<crypto-ed25519>>), and a session key for each direction
from two X25519 key pairs, libsodium's `crypto_kx` (<<crypto-kx>>), with
ChaCha20-Poly1305 for the messages (<<crypto-chacha>>). The handshake's own
steps, Noise's patterns and libp2p's framing, are a domain library's to build
from them, not this library's API.

A peer's identity: the key pair, a signature over what it says, and anyone's
check of it with the public key alone.

*Mistakes to avoid.* A session key pair is drawn for each connection and
never kept: the identity key signs it, so that a stolen identity key does not
open past sessions. A public key received during a handshake proves nothing
until its signature, by an identity the program already trusts, verifies. A
nonce is never repeated under a session key: number the messages of each
direction from zero.

[#crypto-p2p-signed]
=== Proving who wrote a message

*The problem.* Peers exchange messages through a public relay that anyone can
post to. How does a reader know a message comes from its author and was not
changed?

*The idea.* The author signs the message's hash with a secret key; any reader
verifies with the author's public key. A valid signature proves that the holder
of the secret key signed exactly these bytes. Nostr's events, for one, are
signed this way, with BIP 340 over the event's SHA-256
(link:https://github.com/nostr-protocol/nips/blob/master/01.md[NIP-01]).

[#crypto-p2p-session]
=== Agreeing on a key in public

*The problem.* Two browsers want to talk privately through a relay that sees
every byte. They have never met and share no secret.

*The idea.* With elliptic-curve Diffie-Hellman each side combines its own secret
key with the other's public key and arrives at the same 32-byte secret, which
the relay cannot compute from the public keys alone
(link:https://en.wikipedia.org/wiki/Elliptic-curve_Diffie%E2%80%93Hellman[Wikipedia]).
That secret is not a key yet: HKDF turns it into one, bound to the application
by a label (link:https://www.rfc-editor.org/rfc/rfc5869[RFC 5869]). HKDF is a
few lines on Boost.Hash2's HMAC, checked here against the RFC's first test case
before it is used:

*Mistakes to avoid.* ECDH alone does not tell Alice that the public key really
is Bob's: an attacker in the middle can swap both keys and read everything
(link:https://en.wikipedia.org/wiki/Man-in-the-middle_attack[Wikipedia]). Sign
the public keys (<<crypto-p2p-signed>>), or compare a fingerprint out of band.
Never use the shared secret directly as a key, or as several keys: derive one
key per purpose, each with its own label. Draw fresh key pairs for each
session, as the example does: with long-lived key pairs, whoever later steals
a secret key computes every past session's secret from the recorded public
keys, while fresh pairs wiped after the session give *forward secrecy*
(link:https://en.wikipedia.org/wiki/Forward_secrecy[Wikipedia]); a long-lived
key signs the fresh public keys instead. `agree_hashed` returns
libsecp256k1's hashed form, the SHA-256 of the compressed shared point, as a
`secret<32>` that wipes itself: both sides must use the same form, and a
protocol that takes the raw x coordinate, such as Nostr's NIP-44, needs
`agree` (<<crypto-secp256k1-ecdh>>).

[#crypto-p2p-nostr-dm]
=== A shared key in Nostr's direct messages

*The problem.* A Nostr chat app sends a private message to a contact through
public relays, which keep every event and serve it to anyone who asks. The two
users know each other only by their public keys, the secp256k1 keys that sign
their notes.

*The idea.* Each side combines its secret key with the other's public key, an
ECDH, and both find the same shared point. Nostr's encrypted payloads take its
x coordinate unhashed, and derive from it a conversation key, HKDF-extract
with the salt `nip44-v2`, then a key for each message
(link:https://github.com/nostr-protocol/nips/blob/master/44.md[NIP-44]).
`agree` gives the x coordinate as a `secret<32>`
(<<crypto-secp256k1-ecdh>>); the conversation key and everything after it,
the message keys, the padding and the payload's format, are NIP-44's, which a
domain library built on crypto and hash, such as a future webcpp::nostr,
derives. The example computes the conversation key only to show where the x
coordinate goes:

*Mistakes to avoid.* Hashing the x coordinate differently on the two sides:
`agree_hashed` hashes the compressed shared point with SHA-256, libsecp256k1's
default, and a side that uses it while the other takes the raw x coordinate
gets another key, so that every message fails to open with nothing pointing at
the cause. Reusing the conversation key as a message key: it is the same for
every message between the two users, in both directions; NIP-44 derives each
message's keys from it and a fresh 32-byte nonce, and a program that encrypts
with the conversation key itself repeats its keys across messages.

[#crypto-p2p-v2]
=== A handshake an observer cannot recognise

*The problem.* A node of a peer-to-peer network, a Bitcoin node or a
messenger, opens connections that a box on the path may want to recognise and
block. A handshake that starts with a public key is easy to spot: a compressed
key begins with 02 or 03, and its next 32 bytes are always the x coordinate of
a point of the curve, which only about half of all random strings are.

*The idea.* Bitcoin's version 2 transport sends each peer's key as an
ElligatorSwift encoding instead: 64 bytes, made from the key pair and fresh
randomness, that cannot be told from random ones; both peers compute the same
secret from the two encodings
(link:https://github.com/bitcoin/bips/blob/master/bip-0324.mediawiki[BIP 324];
<<crypto-secp256k1-ellswift>>). The secret feeds the protocol's key schedule;
that schedule and the protocol's packets are BIP 324's, a domain library's.

The encodings hide that a key exchange happens, not who takes part: both peers'
addresses stay visible to whoever watches the connection. This section names no
application.

*Mistakes to avoid.* Draw fresh randomness for every encoding: the same key
with the same randomness gives the same 64 bytes, which links two connections
of one node. Pass the two encodings in the protocol's order, the initiator's
first, and name the right party: a side that passes them in its own order
computes another secret, and the connection fails with nothing pointing at the
cause. Never use the secret as a key by itself: BIP 324 derives its session's
keys from it with HKDF.

[#crypto-p2p-handshake]
=== Signed handshakes a browser verifies

*The problem.* A program in {cpp} joins peers that run in browsers, whose
cryptography is WebCrypto: the {cpp} side must sign what a browser verifies,
verify what it signs, and agree on a session key with it. WebCrypto has ECDSA
and ECDH on NIST's P-256
(link:https://www.w3.org/TR/WebCryptoAPI/[W3C Web Cryptography API]), which
is what such peers use: Trystero 0.27.0, a browser library for peer-to-peer
rooms, signs its handshakes with ECDSA on P-256 and SHA-256, makes every
signature low S when it signs
(link:https://github.com/dmotz/trystero/blob/0.27.0/packages/core/src/crypto.ts[Trystero
0.27.0's crypto.ts]) and refuses one that is not when it reads, before it
verifies
(link:https://github.com/dmotz/trystero/blob/8d3f57ef42c3d622840eec479784c99deeeb2d05/packages/core/src/identity.ts#L355[Trystero
0.27.0, packages/core/src/identity.ts, lines 355 and 374]), and derives its pairwise keys from ECDH's 256 bits
through HKDF with SHA-256
(link:https://github.com/dmotz/trystero/blob/8d3f57ef42c3d622840eec479784c99deeeb2d05/packages/core/src/crypto.ts#L303-L328[Trystero
0.27.0, packages/core/src/crypto.ts, lines 303 to 328]).

*The idea.* Each peer keeps a long-lived identity, a P-256 key pair stored as
its 32-byte scalar and made again from it (<<crypto-p256-keys>>), and draws a
fresh key pair for each session. It sends both public keys raw, the 65 bytes
of WebCrypto's `exportKey("raw")`, and the receiver makes each a `public_key`,
which checks the point once. Both sides hash the handshake's bytes with SHA-256
and each signs the digest, marked `+crypto::prehashed{digest}+`, with its
identity, as WebCrypto's ECDSA with SHA-256 signs (<<crypto-p256-ecdsa>>). A
signature has two forms, s and n - s, and both verify; a protocol that
requires one form, low S, gets it from `sign`, which signs no other, and its
receiver refuses the other form with `is_low_s` before it verifies. The session key comes from ECDH's x of the
two session key pairs, which is not a key by itself, through HKDF
(<<crypto-p256-ecdh>>; link:https://www.rfc-editor.org/rfc/rfc5869[RFC 5869]).
The example builds this from the calls of the three P-256 examples; what is
signed, when, and the low-S rule are a protocol's, and Trystero's protocol is
webcpp::trystero's, which lives there, not in this library.

*Mistakes to avoid.* A peer that signs with another implementation, WebCrypto
among them, and does not normalize: about half of its signatures come out
high, so the handshake fails for half the sessions, with nothing pointing at
the cause; such a peer normalizes what it signs, as Trystero does. Checking low S only after the signature verifies, or not at all: the
form of a signature is a second, valid signature anyone can make from the
first, and a protocol that names messages by their signature then sees one
message twice. Using the identity key for ECDH, or keeping the session key
pair: a stolen identity key then opens every past session, while a session key
pair wiped after the handshake gives forward secrecy (<<crypto-p2p-session>>).
Trusting the identity key a peer sends: the signature proves that the sender
holds that key, not that it is the peer the program meant; the program checks
the key against the one it expects.
