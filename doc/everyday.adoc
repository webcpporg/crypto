[#crypto-everyday]
== Everyday applications

Most programs that need cryptography are not about cryptography: a login form,
a shop, a file-sharing app, a program that updates itself. Each needs a few
primitives used exactly right. This chapter gathers them; each section links
to the chapter that teaches the primitive.

[#crypto-everyday-files]
=== A file-sharing app: secret boxes and sealed boxes

*The problem.* A file-sharing app stores files on a server, or in a cloud
bucket, that its users do not control. Whoever runs the storage, or breaks
into it, reads every file, and can change one before the recipient downloads
it. The recipient is known only by a public key, published once; the sender
and the recipient are never online together.

*The idea.* age, a file encryption tool and format, does it this way
(link:https://github.com/C2SP/C2SP/blob/main/age.md[the age format]), and its
TypeScript implementation is built on noble's ciphers and curves: the file is
encrypted once under a key drawn for that file alone, and that file key is
encrypted to each recipient's X25519 public key, with a key pair drawn for
the purpose, so that the recipient's secret key alone recovers it. webcpp's
primitives do the same in libsodium's formats: the file in a secret box
(<<crypto-secretbox>>) under a fresh 32-byte key, and the key in a sealed box
to the recipient (<<crypto-sealed-box>>). Each file has its own key, so a
leaked key opens one file; the tag of each box makes any change to the upload
fail to open, never decrypt to something else. age's own steps, its header,
its recipient stanzas and its chunked payload, are a domain library's to build
from these primitives; this program does not read age files.

*Mistakes to avoid.* Never reuse a file key for a second file, nor a nonce
under one key. Open the file key and the file before using a byte of either: a
box that does not open is an attack or a corruption, never a reason to fall
back on an unencrypted copy. A sealed box says nothing of who sent it: an app
where the sender matters signs the upload (<<crypto-ed25519>>) or uses a box
between the two key pairs (<<crypto-box>>). A large file is sealed in chunks,
each its own box with its own nonce, so that a reader need not hold it whole.

[#crypto-everyday-login]
=== A login: session tokens and reset links

A session token or a password-reset link is a bearer secret: whoever has it is
the user. It is drawn from `random_device`, 32 bytes. The server stores the
token's SHA-256 (Boost.Hash2's `sha2_256`), not the token, and looks the hash up
when the token comes back, so that a leaked database hands out no live session
or reset link (OWASP asks that reset tokens be stored securely,
link:https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html[Forgot
Password Cheat Sheet]); a random token of 32 bytes needs no slow password hash.
`equal` is for a token or a MAC checked against one value the program already
knows. <<crypto-entropy>> shows the program, `reset_token`.
A password itself is never encrypted: it is hashed with a slow password hash,
Argon2id or scrypt, which
link:{webcpp-libs}/hash/{webcpp-page}#hash-password-hashing[webcpp::hash's password hashing] gives, not
crypto.

[#crypto-everyday-webhook]
=== A webhook: checking an HMAC

A payment provider or a source-code host signs each call to a program's
webhook with an HMAC under a shared secret. The program recomputes it with
Boost.Hash2 and compares with `equal`, never `==`: <<crypto-equal>>.

[#crypto-everyday-storage]
=== A database field, a cookie, a file

Data stored where someone else may read it, a database, a cookie, a cloud
bucket, is sealed with AES-GCM, with what it belongs to (the user's id, the
cookie's name, the file's path) as additional data, so that it cannot be moved
to another place: <<crypto-gcm>>. A large file is sealed in records:
<<crypto-gcm-incremental>>.

[#crypto-everyday-update]
=== A software update or a licence file

*The problem.* A program downloads its updates, or reads a licence file. Anyone
who can change the download, a compromised mirror, a network in the middle,
could ship code that the program then runs.

*The idea.* The publisher signs the SHA-256 of each update with ECDSA; the
program ships with the publisher's public key and accepts an update only when
its signature verifies. Only the publisher's secret key can produce a signature
the program accepts.
