[#crypto-key-exchange]
== Key exchange: `webcpp::crypto::key_exchange`

*Key exchange* gives two parties who swapped public keys the keys a cipher
needs, without sending any of them. The namespace
`webcpp::crypto::key_exchange` holds libsodium's `crypto_kx` in this version: a
construction over X25519 (<<crypto-x25519>>) and BLAKE2b rather than a curve
primitive, so it is not in `curves`, and named by the problem it solves.

include::generated/namespace-key_exchange.adoc[]

[#crypto-kx]
=== crypto_kx

`<webcpp/crypto/key_exchange/kx.hpp>` is libsodium's key exchange,
`crypto_kx`, on libsodium (`/third_party//sodium`, or
`/webcpp/crypto//kx-default`, which links it on every target), in the namespace
`webcpp::crypto::key_exchange`. It turns X25519 (<<crypto-x25519>>) into what
a program that talks to one peer needs: two keys ready for a cipher, one for
each direction. A chat app's client and its server each hold a
`kx_keypair`; they send each other their public keys; the client calls
`client_session_keys(server_public_key)` and the server
`server_session_keys(client_public_key)`. Each gets a `session_keys`, a
`receive` and a `transmit` key, both `secret<32>` that wipe themselves; the
client's `transmit` is the server's `receive` and the reverse, so that a
message each side sends has a key of its own
(link:https://doc.libsodium.org/key_exchange[libsodium's documentation, key exchange]).

The session keys are BLAKE2b-512 of the X25519 shared secret and of both
public keys, client first, split in two: unlike the raw shared secret of
`agree` they are keys, and they bind both public keys. Only another `crypto_kx`, as
libsodium's own in another language, derives the same keys; a protocol that
names X25519 and a KDF of its own, as TLS 1.3's key schedule does
(link:https://www.rfc-editor.org/rfc/rfc8446#section-7.1[RFC 8446, section 7.1]),
uses `agree` instead.

`kx_keypair<>::generate()` draws the key pair's 32-byte seed with
`random_device`; `kx_keypair<>::derive_from_seed(seed)` makes the same key pair from the
same seed, as a program that keeps its seed does. A peer's public key of low
order makes the X25519 secret all zero, whatever the secret key: both
functions refuse it with `weak_public_key`, as libsodium does (design D8).

*Pitfalls.*

* The two sides must agree on who is the client: two clients, or two servers,
compute keys that do not match, and every message fails to open.
* `crypto_kx` proves nothing about who sent a public key: an attacker in the
middle exchanges keys with each side. A protocol signs the public keys, or
checks them against keys it already trusts.
* A session key is used with one nonce per message: a counter that starts at
zero is enough for ChaCha20-Poly1305, since each direction has its own key; a
key pair kept across sessions gives the same keys again, so a program that
reconnects starts from a fresh key pair, or uses XChaCha20-Poly1305 with
random nonces.
