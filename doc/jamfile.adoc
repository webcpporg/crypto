[#crypto-jamfile]
== Using webcpp::crypto in your Jamfile

The rule, in three lines:

. A program names `/webcpp/crypto//crypto` and the library of each backend it
uses: `/third_party//bearssl`, `/webcpp/crypto//openssl`,
`/third_party//ctaes` or `/third_party//secp256k1`. A program that only draws
random bytes or compares tags names `/webcpp/crypto//crypto` alone.
. BearSSL, ctaes and libsecp256k1 build for every target; OpenSSL builds
natively, on wasip2 and on wasip3, and never for Emscripten, where the build
stops and says to name BearSSL.
. A backend named and never called adds no byte to the program.

crypto is header-only, and webcpp builds every backend from its sources, file
by file: OpenSSL statically, from the superproject's `third_party/libs/openssl`,
never the system's. The target `/webcpp/crypto//crypto` adds crypto's
`include` directory, Boost's headers and webcpp's configuration, and on Windows
the system library `bcrypt`, through which `random_device` reads Windows'
generator.

In {cpp}, a program names a backend by including its header,
`<webcpp/crypto/backends/<name>.hpp>`, and using its tag type,
`backends::<name>`, as a template argument:
`ciphers::gcm<ciphers::aes256<backends::bearssl>>`. The default backend needs no
include of its own: `<webcpp/crypto/ciphers/aes256_gcm.hpp>` brings it when it is
linked.

[#crypto-jamfile-default]
=== The default backend, and choosing another

`aes128_gcm`, `aes256_gcm` and `aes256<>` name AES-GCM's default backend:
natively OpenSSL, on WebAssembly BearSSL, whatever else the program links
(<<crypto-backends-defaults>>). A program that wants another backend names it
in the type, as `ciphers::gcm<ciphers::aes256<backends::bearssl>>`, and links
it; no define chooses a default. A native program that links BearSSL alone and
uses `aes256_gcm` stops where it calls it, with the line that links OpenSSL
and the type that names BearSSL. Version 0.1's
`WEBCPP_CRYPTO_DEFAULT_BACKEND_BEARSSL` and
`WEBCPP_CRYPTO_DEFAULT_BACKEND_OPENSSL` stop the build with the type to write
(<<crypto-jamfile-messages>>).

A program built for every target links its default with one line,
`/webcpp/crypto//gcm-default`, which links OpenSSL natively and BearSSL on
WebAssembly, the library of the backend `aes256_gcm` names on each target; the
examples of this page link it so. The whole Jamfile of the fixture
`gcm_default`, built and run on native, wasip2, wasip3 and Emscripten
(<<crypto-jamfile-cases>>):

[listing]
----
include::{webcpp-root}/tools/test/fixtures/crypto_jamfiles/gcm_default/Jamfile[tag=jamfile]
----

Each family with a default has such a line, `/webcpp/crypto//<family>-default`
(`secp256k1-default` too), generated with the defaults from the same table.

The source-built OpenSSL is compiled without assembly (`no-asm`) on MSVC,
wasip2 and wasip3: its AES is table-based and its GHASH 4-bit, neither constant
time, and there is no AES-NI. A program for which timing attacks matter on
MSVC names `ciphers::gcm<ciphers::aes256<backends::bearssl>>`.

[#crypto-jamfile-memory]
=== OpenSSL's memory option

A native program that sends OpenSSL's allocations to its own resource
(<<crypto-memory-openssl>>) gives the define
`WEBCPP_CRYPTO_OPENSSL_MEMORY_RESOURCE` and `/webcpp/crypto//openssl`
together, in the requirements of its project, not of one target. Every target
of the program then gets both: its own libraries, and a tool that only calls
`random_device` or `equal`, which would otherwise have the define without
OpenSSL. The fixture `memory_option` builds and runs this Jamfile natively:

[listing]
----
include::{webcpp-root}/tools/test/fixtures/crypto_jamfiles/memory_option/Jamfile[tag=jamfile]
----

Each mistake stops the build, with the messages of
<<crypto-jamfile-messages>>: the define on a target without OpenSSL, or in a
build for WebAssembly, is refused by `config.hpp`; `openssl_memory_resource()`
not defined is a link error; and on MSVC, files of one program compiled some
with the define and some without are refused by the linker (`LNK2038`). These
requirements cannot be built for WebAssembly, since the option is refused
there and `/webcpp/crypto//openssl` stops an Emscripten build: a WebAssembly
build of the same program is a project of its own, in a directory of its own,
with neither the define nor OpenSSL, and names `/third_party//bearssl`.

[#crypto-jamfile-cases]
=== Every Jamfile a user writes

Each case below is a fixture of the superproject's
`tools/test/crypto_jamfiles_test.py`: its Jamfile is built on a scratch copy of
the superproject, as a user's would be, on each target named, and the program
run; what it prints is checked. The list is generated from the fixtures.

include::generated/jamfiles.adoc[]

A user builds a case from its directory with `b2` natively,
`b2 toolset=emscripten` for the browser, and `b2 toolset=clang-wasip2` or
`b2 toolset=clang-wasip3` for WASI, and runs the program as each target runs one:
`./app`, `node app.js`, or a WASI runtime such as wasmtime. The cases `web`,
`server` and `gcm_default` are one program, byte for byte (the test checks the
copies), whose output names the backend that ran: BearSSL, the default on
WebAssembly, and OpenSSL, the default natively; `gcm_default` links whichever
the target needs. `both_bearssl_named` links both and names
BearSSL in the type where OpenSSL is the default. On WASI the default is
BearSSL even when OpenSSL is linked (<<crypto-backends-defaults>>), so `server`
is a native case; a WASI program that wants OpenSSL names the backend in the
type, as `openssl_linked` does.

The examples of this page are built the same way: `example/Jamfile` names
`/webcpp/crypto//crypto` in its project's requirements, and each example the
libraries of its backends. The program of <<crypto-gcm>>, for instance, names
BearSSL:

[listing]
----
include::{library-root}/example/Jamfile[tag=aes256_gcm_bearssl]
----

[#crypto-jamfile-messages]
=== Every message, and its fix

A mistake in a Jamfile stops the build with a message that says what to add.
At compile time, the first error is the one to read: the lines after it come
from it and go away with it. At link time, a symbol whose name is the
instruction reports a backend library that is missing, or of another commit or
configuration than the headers; with b2 it cannot happen, and it guards
builds made by other means. Everything below is generated from the tests that
fix each text.

[#crypto-jamfile-windows]
=== Windows

crypto's headers include `<windows.h>` under `NOMINMAX` and
`WIN32_LEAN_AND_MEAN` when the program has not defined them, and write
`(min)()` and `(max)()` so that the macros never matter. A program that wants
the macros `min` and `max`, or what `WIN32_LEAN_AND_MEAN` leaves out, includes
`<windows.h>` itself before any header of crypto.
