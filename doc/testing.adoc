[#crypto-testing]
== Testing

crypto is tested by lightweight_test programs under `test/`, each declared in
`test/Jamfile`, and each public header is compiled alone, as the only include
of its translation unit, with the libraries it needs. Every test program is
built twice, with exceptions and with `exception-handling=off`, by the
Jamfile's rule `crypto-run`. Every example of this page is built and run, and
its output compared with its `.expected`.

Each lane builds from scratch, as the continuous integration does, from the
root of a webcpp checkout:

`b2 -a --build-dir=bin/lane-native libs/crypto/test libs/crypto/example`::
The {n-tests-native} tests and {n-examples-native} examples natively, and each
of the {n-headers} public headers compiled alone.

`b2 -a --build-dir=bin/lane-wasip2 toolset=clang-wasip2 testing.launcher=tools/boost/asio-wasip2/run.sh libs/crypto/test libs/crypto/example`::
The same for wasm32-wasip2: {n-tests-wasip2} tests, each run by wasmtime.
`toolset=clang-wasip3` with `tools/boost/asio-wasip3/run.sh` does the same for
wasm32-wasip3: {n-tests-wasip3} tests.

`b2 -a --build-dir=bin/lane-emscripten toolset=emscripten libs/crypto/test libs/crypto/example`::
The same on Emscripten: {n-tests-emscripten} tests, each run by node.

MSVC and Apple Clang run in the continuous integration only. The own lane
`c-suites` runs the C libraries' own test suites (BearSSL's, ctaes's and
libsecp256k1's) on webcpp's build of them, on every target, on every push:
the target's lane command with `libs/crypto/test/c_suites//c-suites` in place
of the two directories. libsodium's own suite runs in webcpp::hash's lane
`c-suites` (`libs/hash/test/c_suites//c-suites`), on every target, against the
same build of libsodium that crypto links: each program of its `test/default`,
those of crypto's operations among them (`sign`, `box`, `box2`, `box7`,
`box8`, `box_easy`, `box_easy2`, `box_seal`, `secretbox`, `secretbox2`,
`secretbox7`, `secretbox8`, `secretbox_easy`, `secretbox_easy2`, `xchacha20`,
`aead_chacha20poly1305`, `aead_chacha20poly13052`, `aead_xchacha20poly1305`,
`kx`, `scalarmult`, `ed25519_convert`, and `codecs`, the base64 functions
PEM's engine calls), compared with its `.exp`. The own lane `constant-time`
checks constant time (<<crypto-backends-constant-time>>): natively, Valgrind
and clang's MemorySanitizer on Linux and dudect's statistics on Linux and
macOS, and dudect's under wasmtime on wasip2, whose |t| a runner GitHub hosts
prints without judging it (<<crypto-backends-constant-time>> says why); the
native lane's command with `libs/crypto/test/constant_time//constant-time` in
place of the two directories.

What the tests check:

* *The vectors.* AES-GCM against the GCM specification's cases and Project
Wycheproof's vectors, on BearSSL and on OpenSSL; AES against FIPS 197 on ctaes
and OpenSSL; secp256k1 against BIP 340's vectors, Wycheproof's ECDSA, ECDH and
DER vectors and libsecp256k1's own recovery edge cases, the x-only tweak against
BIP 341's, the tweaks, negations and sums of keys against libsecp256k1's C API,
and the SPKI and PKCS#8 encodings against Wycheproof's SPKIs, OpenSSL (natively
and on WASI) and node's `crypto` module (under Emscripten). Ed25519 against RFC
8032's tests, Wycheproof's EdDSA vectors and the twelve edge cases of "Taming
the many EdDSAs"; X25519 against RFC 7748's and Wycheproof's; ChaCha20-Poly1305
and XChaCha20-Poly1305 against RFC 8439's and the XChaCha20 draft's examples and
Wycheproof's vectors, on every backend that has them.
* *node's WebCrypto as an outside oracle,* on Emscripten: 200 Ed25519 key
pairs, messages and signatures from a fixed seed, each verified and signed
again by `crypto.subtle`, which must give the same public key and signature,
and 200 X25519 agreements, each derived again to the same public key and
shared secret (`oracle_25519`, which prints `oracle ok 400`).
`oracle_25519_corrupted` flips one signature and one shared secret, and
passes only when WebCrypto disagrees on exactly those two.
* *The backends against each other,* on random keys, IVs, additional data and
messages of every size around a block's: BearSSL and OpenSSL seal the same
bytes with AES-GCM and each opens what the other sealed, with BearSSL on its
x86-64 instructions and on its portable code; ctaes and OpenSSL encrypt the
same blocks. Natively, on wasip2 and on wasip3, from a fixed seed and from a
seed drawn at each run, which a disagreement prints.
* *`<windows.h>`,* bare, included before and after every public header with
every backend linked: no macro of it breaks a header, and the headers leave
`NOMINMAX` and `WIN32_LEAN_AND_MEAN` as they found them. Its teeth are on the
continuous integration's MSVC lanes.
* *Every guard and every error,* on a mock backend whose checks every real
backend's test runs as well, and the limits natively.
* *Allocation:* every `operator new` and the C library's allocator counted
around each operation.
* *The default backend* of every family on every target, the same with every
backend linked, with none, with each alone and with the defines that no longer
choose one (<<crypto-backends-defaults>>).
* *Every message,* word for word, by a message test with clang on the targets
it names; on MSVC, each case proven to stop the build
(<<crypto-jamfile-messages>>).
* *The user's Jamfiles,* by the superproject's
`tools/test/crypto_jamfiles_test.py`, which builds each fixture on a scratch
superproject (<<crypto-jamfile-cases>>).
* *A backend named and not called adds no byte,* by programs built with and
without its library and compared.

The documentation's tables are checked by its build: `doc/tables/generate.py
--check` fails when a generated table differs from what the data and the tests
give.

The test matrix of every lane is published with the documentation, at
https://webcpporg.github.io/report/.
