[#crypto-backends]
== The backends

A backend is a C library that crypto wraps; the program links the ones it
names in its Jamfile, and webcpp builds each from its sources, file by file.
Every table of this chapter is generated (`doc/tables/generate.py`) from
committed data and from the tests themselves: an operation is supported on a
backend and a target exactly where a test program that runs it is declared for
that target, and refused where a message test stops it. The data and the
tables are regenerated, and checked by the documentation's build, at every
change of a test or a pin.

A program asks the same table in {cpp}: `supports_v<Algorithm, Backend>`, in
`<webcpp/crypto/supports.hpp>`, is `true` exactly where the table says that
the backend has the algorithm on the target being compiled, and needs neither
the backend's header nor its library, so that generic code can choose a
backend at compile time. Each algorithm's type names its family and its
algorithm for it (`family_type` and `name_type`, tags of `families` and
`tags`); the test that asserts every cell is generated from the same data.

[#crypto-backends-facts]
=== What each backend is

include::generated/backend-facts.adoc[]

OpenSSL is never the system's: the superproject builds it from
`third_party/libs/openssl`, statically, natively and on wasip2 and wasip3, and
`/webcpp/crypto//openssl`, crypto's name for it, stops the build on Emscripten.
Natively with Clang and GCC it is built with its assembly; on MSVC, wasip2 and
wasip3 it is built `no-asm`
(link:https://github.com/openssl/openssl/blob/master/INSTALL.md[INSTALL.md]).
BearSSL zeroes nothing it computes on the stack: its ECDSA signing keeps the
scalar, the nonce and the HMAC-DRBG state that derives the nonce in its own
stack frame and returns without clearing them
(link:https://www.bearssl.org/gitweb/?p=BearSSL;a=blob;f=src/ec/ecdsa_i31_sign_raw.c;hb=7bea48e5e850ab4cafbe68d3765cdaba13a86d6f#l45[ecdsa_i31_sign_raw.c,
lines 45 to 51 and 115 to 135]). webcpp wipes what it owns, a key pair's state
and every `secret<N>`, and cannot reach a callee's frame, which the program's
next calls overwrite.

BearSSL's P-256 code differs by target. Natively webcpp takes `br_ec_p256_m62`,
whose field arithmetic multiplies 64-bit words into a 128-bit product, where
BearSSL compiled it (a compiler with `unsigned __int128`, or MSVC's
`_umul128`), and `br_ec_p256_m31`, 32-bit words, where it did not. On
WebAssembly it takes `br_ec_p256_m31` always: wasm32 has no 128-bit product,
the compiler makes it a call into its runtime library, and BearSSL states the
constant time of its multiplications only for the instructions it names
(link:https://www.bearssl.org/ctmul.html[BearSSL, constant-time
multiplications]). Both are constant time by BearSSL's design, and the lane
below times the 64-bit code natively and the 32-bit code under wasmtime. ECDSA
is BearSSL's `br_ecdsa_i31_sign_raw` and `br_ecdsa_i31_vrfy_raw` on every
target, over the curve code chosen.

[#crypto-backends-bearssl-fix]
webcpp's BearSSL is upstream's commit `7bea48e` with one fix of webcpp's, on
the branch `webcpp` of its mirror
(link:https://github.com/webcpporg/bearssl/commit/32381d6e787a32cbb7a687246349200d78b8ff7c[webcpporg/bearssl
32381d6]). Upstream's ECDSA signing reads RFC 6979's nonce through
`br_ecdsa_i31_bits2int`
(link:https://www.bearssl.org/gitweb/?p=BearSSL;a=blob;f=src/ec/ecdsa_i31_bits.c;hb=7bea48e5e850ab4cafbe68d3765cdaba13a86d6f#l44[ecdsa_i31_bits.c,
lines 44 and 45]): `br_i31_decode` writes the nonce's actual bit length into
the integer's header, and `br_i31_rshift` then runs its loop and its last
store over the words that length needs, 8 rather than 9 for a P-256 nonce
below 2^248^, one signature in about 256. A signature's time then tells whether
its nonce is short, the leak a lattice turns into the key from enough timed
signatures
(link:https://minerva.crocs.fi.muni.cz/[Minerva, CVE-2019-15809]).
The fix sets the header back to the order's length before the shift, which
then runs over every word: the words above the nonce are zero, so the nonce is
unchanged. The constant-time lane below found the leak on 2026-11-21 under
memcheck and MemorySanitizer; dudect, which would see one measurement in about
256 differ by a few instructions, did not. The 15-bit copy, which webcpp does
not call, has the same fix. Each move of BearSSL's pin carries the commit
until upstream has it.

A program has one copy of each library: libsecp256k1's tables and OpenSSL's
state are global symbols, so webcpp's build is never linked with another copy.

libsecp256k1's precomputed tables are a size knob, the feature
`webcpp-secp256k1-tables`: `auto`, the default, small on Emscripten and large
elsewhere; `small`; or `large`. libsecp256k1 documents the trade: a larger window
means a larger precomputed table and faster verification
(link:https://github.com/bitcoin-core/secp256k1/blob/master/configure.ac[configure.ac]);
the sizes and speeds of webcpp's two settings are not measured yet; the fixtures
`sign` and `sign_small` of <<crypto-jamfile-cases>> build both. The tables
enter the canary, so a program cannot be linked with tables other than those it
was compiled for. With MSVC the static library needs `SECP256K1_STATIC`, which
the target's usage requirements define.

[#crypto-backends-constant-time]
=== Constant time

A cryptographic implementation is *constant time* when its running time and
its memory accesses do not depend on secret data; otherwise a timing attack
can recover the key (link:https://en.wikipedia.org/wiki/Timing_attack[Wikipedia];
link:https://www.bearssl.org/constanttime.html[BearSSL's explanation]). Each
backend's design is stated by its library's documentation, with its source.
The table's per-target columns say what the own lane below runs on each
backend and target, by checker and family, from the documentation's data, the
same as each chapter's comparison table; "not measured yet" where the lane runs
nothing. memcheck and MemorySanitizer run on Linux alone, so their native cells
are Linux's. What the lane measured where a family differs from its backend's
design is listed under the table.

include::generated/constant-time.adoc[]

The own lane `constant-time` (`libs/crypto/test/constant_time`) checks the code
as webcpp compiles it. On Linux, it marks the keys, the seeds, the data and the
tag secret under Valgrind's memcheck, as
link:https://github.com/agl/ctgrind[ctgrind] does, and, in a clang build, under
MemorySanitizer, which only clang has (a gcc build runs memcheck alone): any
branch or memory index that depends on them fails the run. The lane covers
`equal`, `is_all_zero` and the wipe of `secret<N>`; BearSSL's AES-GCM and
ChaCha20-Poly1305 `make`, `seal` and `open`; OpenSSL's `make` and `seal` of
both; ctaes's AES; libsodium's Ed25519 key pair and signature, X25519's public
key and agreement, its three ChaCha20-Poly1305 AEADs and two secret boxes,
`hybrid::box` in both families, the sealed box's `seal` and `open`, and `kx`;
libsecp256k1's own `ctime_tests.c`; and webcpp's code around libsecp256k1:
the key pair's making, its BIP 340, recoverable and hedged ECDSA signatures and
x-only tweak, ECDH in its three forms, the secret key's tweaks and negation,
PKCS#8's encoding and decoding, ElligatorSwift's `ellswift_create` and
`ellswift_xdh`, MuSig2's `nonce_gen` and `partial_sign`, and silent payments'
`create_outputs`, `create_label` and `scan_outputs`, with the wipe of their
workspaces; and BearSSL's P-256: the key pair's making, `sign_ecdsa` followed by
`normalize_ecdsa` and `check_low_s` on the fresh signature, `ecdh_x` and
`decode_pkcs8`. Both checkers run the same paths, written once (`paths.hpp`),
memcheck OpenSSL's besides. Each check is shown to fail on a planted branch on
a key byte, and on a copy of P-256's range check of a scalar that returns at
the first byte that differs, and each path's output is checked to carry the mark, so that the
path is traced, where the checker's shadow keeps it: MemorySanitizer's loses
the mark through a constant-time reduction to one bit, so the result of
`is_all_zero`, X25519's public key, P-256's public key and `ecdh_x` (BearSSL
selects a window's points with masks of that form) and the bytes a destructor
wiped are checked by memcheck alone. dudect's statistics
(link:https://eprint.iacr.org/2016/1123[Reparaz, Balasch and Verbauwhede]) time
BearSSL's two AEADs' seal and open, BearSSL's P-256 `sign_ecdsa` and
`ecdh_x` against the key pair's scalar, ctaes, `equal`, libsodium's X25519
agreement and Ed25519 signing, and libsecp256k1's `ecdh_x` natively, on Linux
and macOS, and under wasmtime.
dudect's programs set nothing themselves: they measure what a program gets,
which on 64-bit ARM is the DIT webcpp sets in each call (<<crypto-backends-dit>>).
Each prints whether the CPU has DIT, and fails where DIT is set on its thread
outside the measured calls, which would measure something a program does not
get. The lane's `dudect_planted` shows that DIT does not hide a leak: X25519's
`agree` after an early-exit scan of its secret key, the scan run inside the
library's own guard as a public operation's code would be, which dudect must
find: |t| 66.72 and 65.53 against the threshold 10 (2026-11-21 UTC, two runs,
an Apple M5 Max, a release build). BearSSL's P-256, its `sign_ecdsa` and its `ecdh_x`
timed against the key pair's scalar, a fixed one against random ones, read |t|
2.24 to 2.29 and 1.84 to 2.19 natively and 1.36 to 2.51 and 1.85 to 2.08 under
wasmtime on wasip2 against the same threshold (2026-11-21 UTC, two runs each,
the lane's among them, on the same machine shared and loaded, a release
build).

memcheck and MemorySanitizer last ran the lane on 2026-11-21 UTC with the
command the CI runs it with, in an arm64 Linux container (Ubuntu 24.04, the
image `linux-lint:arm64` of webcpp's Linux lint, Valgrind 3.22, clang 18), on
an Apple M5 Max. Every path above passed under both, P-256's with webcpp's fix
to BearSSL (<<crypto-backends-bearssl-fix>>); the run before, without it, both
reported the nonce's leak. Each planted program failed where it must, and the
lane's dudect programs passed there too: P-256's `sign_ecdsa` |t| 1.91 and
`ecdh_x` 1.96, with `dudect_planted` at 34.89.

One measurement is an open finding, listed under the table with its numbers:
libsodium's X25519 `agree` under wasmtime, on wasip2. Its cause is measured:
wasmtime does not set DIT, and with DIT set in wasmtime's main thread, an
experiment and not the lane, the case passes. The WebAssembly cannot set it,
so the lane prints its value on wasip2 without judging it, and judges
everything else.

dudect's two classes differ in the secret's bytes and in nothing else: the
preparation of each measurement reads both inputs and writes the secret with
the same instructions whatever the class, since anything a class does
differently before the measured call shows in its time. On a runner GitHub
hosts, a virtual machine shared with other tenants whose processor changes from
run to run, a program prints each dudect |t| with its evidence and does not
judge it, since a verdict from one process would pass or fail with the machine
drawn: measured there on 2026-11-20 on three processors, 23 runs of 24 stayed
below 4.4 and one read 69.8, on both seeds, on a case below 4.4 in every other
run. The research's hypothesis is a layout effect, which a fresh process
(other addresses) varies, so the CI's `dudect_judge.py` warns for every |t| of
10 or more, measures such a case again in two fresh processes and fails when
two of the three values are 10 or more, naming the case and its values. Each
program but `dudect_planted` also measures an A/A control case, whose classes
are prepared by the same instructions with the same value: it shows what the
machine itself does. Valgrind's memcheck and MemorySanitizer, which do not
measure time, are judged there; dudect is judged by the program itself
wherever else the lane runs, on a machine of one's own, in one process.

Whether a tag matched, or a shared secret came out all zero, is public by
design, since the operation reports it, but it is computed from the secrets: it
is the one kind of value webcpp marks public, where webcpp's code first
branches on it (BearSSL's engines, libsodium's engines, X25519's `agree`,
P-256's range check of a scalar and its low-S test, and each verdict of
libsecp256k1's that webcpp reads), so that the checkers report every other
branch. A signature is public once it is made, but one fresh from
`sign_ecdsa` is computed from the scalar: `normalize_ecdsa` and `check_low_s`
mark their verdict public, so that a program that checks its own signatures
under a checker sees no report. libsecp256k1 marks its own public values (a nonce's retry,
a verdict, a public key it loads) when its context is made with
`SECP256K1_CONTEXT_DECLASSIFY`, which webcpp's contexts are under the
checkers, as its `ctime_tests.c` makes its own; a key pair's public key and a
silent payments label, which webcpp reads from libsecp256k1's structures, are
marked public where webcpp reads them. libsodium branches on its own
verdicts inside the functions that compute them; the lane tells memcheck of
each of those functions (`sodium_verdicts.supp`), and libsodium is used
unchanged. BearSSL's ECDSA signing does the same with its scalar's decoding
and RFC 6979's retry of a nonce out of range, in `br_ecdsa_i31_sign_raw`
(`bearssl_verdicts.supp`). MemorySanitizer approximates a subtraction without its carry, so it
counts every such verdict public by itself: memcheck is the check of the
marks. OpenSSL's verdict is OpenSSL's own internal
branch, which webcpp cannot mark: OpenSSL is checked with the key secret during
`seal` only.

[#crypto-backends-dit]
==== Data-independent timing (DIT)

64-bit ARM's DIT (data-independent timing) bit, PSTATE.DIT, makes the
instructions Arm lists take a time independent of their data, and Apple
requires it of constant-time code
(link:https://developer.apple.com/documentation/xcode/writing-arm64-code-for-apple-platforms#Enable-DIT-for-constant-time-cryptographic-operations[Apple, enable DIT for constant-time cryptographic operations]).
None of the C libraries sets it, so webcpp does: every public function that
runs a backend's cryptographic code, and `equal`, runs its whole body with DIT
set on 64-bit ARM under macOS, iOS, Linux and Android where the CPU has
FEAT_DIT (`hw.optional.arm.FEAT_DIT` on Apple's systems, `HWCAP_DIT` on
Linux), and returns with the thread's DIT as it found it: clear when it was
clear, set when the program set it itself (Apple's
`timingsafe_enable_if_supported`, from macOS 15.2) or an outer call did. An
error and an exception leave it as found too, and DIT is a thread's own
state, so a call never changes another thread's. A program does nothing.

Elsewhere webcpp sets nothing:

* On x86, the counterpart is Intel's DOITM (data operand independent timing
mode), a model-specific register that only the kernel writes: it is the
system's choice, out of webcpp's reach.
* On WebAssembly, the engine that compiles the code decides, and the
WebAssembly cannot set DIT: X25519 on wasip2 is the open finding above.
* On Windows on ARM64, no documented way to ask Windows whether the CPU has
FEAT_DIT was found, and DIT's instructions trap on a CPU without it: the
guard is empty there, and untested.

What the guard adds to a call, measured from a release build beside the
shortest operation's time, is in <<crypto-performance-timing>>.

`silent_payments::scan_outputs` calls the program's `LabelLookup` inside its
guard: the lookup runs with DIT set, which only makes it data-independent too.

The lane's dudect used to set DIT itself; it now sets nothing and
measures the library's guard. libsodium's X25519 `agree`, an all-zero secret
key against random ones, on an Apple M5 Max from a release build, against the
threshold 10: with the library's guard, |t| 1.8 to 2.8 (2026-11-21, five runs);
with no DIT at all, |t| 4.3 to 7.8 (2026-11-21, three runs), below the
threshold but higher, and 6.7 to 14.5 (2026-11-19), above it; with the
harness setting DIT, as the lane did before, |t| 1.5 to 2.4 (2026-11-21, three
runs). Dates are UTC.

=== Size

What each cell of the capability table adds to a program, per target: a
program per family and backend calls the family's fixed operation once
(`test/sizes/`), and its size is read against a baseline, the same harness
around an operation that calls nothing of crypto, so that a cell is its
operation's code alone. The own lane `sizes` measures them from release builds
alone (`variant=release`, the superproject's `webcpp.program-sizes`), and the
table is generated from what it wrote; a cell it has not built says so. Like
the throughput below, it is a dated reference that decides nothing: a family's
default is chosen by the reason <<crypto-backends-defaults>> states.
